## 已确认：动态空闲归篇与撤回保留深度

- 会话是长期容器，归篇只是其中一段的收束；建议聊天历史继续连续可见，不因归篇清空会话或强制开新窗口。
- 例：10:00 发消息，14:00 又发，则默认归篇时刻顺延到 19:00；在此前继续发会再顺延。收束后下一条属于新的一篇，不另生成空白篇。相邻间隔恰好等于时限时，建议按到期处理。
- 每个会话的空闲阈值独立，默认 5 小时；与快捷窗“关闭后恢复 5 小时”是不同设置，不能串用一个计时器或偏好。
- AI 建议只有用户新发言（含重新编辑后重发的消息）更新空闲计时；查看、输入未发送、撤回、修改旧消息、系统提示和“过去的我”自动投递不刷新。撤回也不自动重排已经形成的篇目；这些边界尚未由用户逐项确认。
- 应用关闭后建议依据持久的最后发言时间补判归篇，无需为结篇强制保持窗口开启。调整阈值对历史篇目的影响仍待定；建议默认影响后续，不自动重切历史。
- 用户要求模仿微信/QQ 的撤回并保留记录，随后已选择：只留撤回提示，原文仅短暂用于重新编辑。不提供长期查看撤回原文或恢复原消息的历史入口。重新编辑的具体短期时长与撤回是否有限时尚未确定；AI 建议文字原文可暂留 5 分钟，过期清理，这不是已确认数值。
- AI 建议聊天原位置显示“你撤回了一条消息”，文字可“重新编辑”回到输入区，再次发送是新消息；撤回提示记录原发送与撤回时间，引用/回顾不继续直接展示已撤回原文。永久删除与撤回分开定义。
- 实施约束建议：短期缓存与正式消息状态分开；撤回后正式可读内容/媒体展示引用不再包含原文，缓存过期清理，不把原文偷偷写入长期撤回审计或通用修订历史。引用摘要、搜索索引、导出和未来投递须同步处理。共享附件的其他有效引用不能被误删；既有备份可能包含撤回前数据，其清理策略需单独明确，不能声称撤回能抹去所有备份。

## AI 建议：先明确关系，不先锁定物理格式

建议消息发送立即可靠保存；将“落盘”“已确认的空闲归篇”“备份”“未来投递”四个时钟分开。这样不会因归档间隔较长而丢失刚发的内容，也不把重复归档或重试当成新消息。

以下是概念关系，均为待讨论方案，不是现行字段定义：

| 概念          | 作用与建议保留的信息                                                                         |
| ------------- | -------------------------------------------------------------------------------------------- |
| 会话          | 稳定身份、可改名称/头像/说明、默认分类、归档规则、可选回顾规则；一个会话可跨日跨年           |
| 原消息        | 稳定身份、所属会话、原发送时间及当时时区、当时作者名/头像、文字及媒体块、引用目标、状态/修订 |
| 日记关联/分段 | 指出哪些原消息归于一段或一篇；建议映射同一来源，避免每次整理复制出无来源的第二份内容         |
| 投递事件      | 原记录引用、规则身份、预定与实际送达时间、未读/已读；去重依据独立于原发言时间                |
| 现在的回复    | 一条有当前时间与当前身份的新消息，链接历史原消息或日记，不改旧消息发送日期                   |
| 媒体          | 复用稳定 media ID 指向图片/表情包/附件；不依赖之后可能失效的磁盘路径或网络 URL               |

每次发送一个稳定消息并不意味着每条必须成为一篇普通日记。本方案修正 MULTI-ENTRY-REQUIREMENTS.md 早先“发送即一条稳定记录”可能造成的歧义；该旧建议没有得到用户对物理存储形式的确认。

建议共用身份、媒体、引用、分类/标签、检索、权限/隐藏边界、备份与 AI 数据接口，再按类型保留专有字段：日记有标题正文，消息有会话/作者/时间/引用，待办有完成状态/截止时间，日程有起止/重复规则。用户可见的统一不要求强行全部塞进日记正文，也不预先规定只能使用一个数据库文件。现有 JSON、未来 SQLite 或混合存储的取舍，需要在容量、并发、检索、备份和手机往返要求清楚后决定。

## AI 建议：过去的我如何发来消息

例如某年 10 月 15 日 20:30 发出一条消息；设定一年后回送，则下一年对应时间出现一条带原日期、当时名字和头像的“过去的我”来信。用户现在回复，回复时间属于现在，并链接到那条原发言。同一来源可有多次投递，但不重复创建原消息，也不把历史发言伪装成当前新写内容。

投递可以表现为同会话中的来信或单独“过去的我”会话，用户还未选择。过去日记可用原文卡片并链接原篇；摘要/改写/AI 生成不属于本轮已确认行为。用户说的三个月/一年同日同时是回顾触发思路，不自动等于要求 AI 或真正联网发送消息给别人。

重要语义留待后续确认：自然月/自然年还是固定天数；时区变化和夏令时；月末/闰日；一次或周期回送；是否全量回送或按会话挑选；离线时下次启动补到收件箱，还是需要未来配置常驻调度/系统通知。只运行本地且退出全部进程时无法保证准点弹窗；当前没有创建任何自动任务。

## 撤回、引用与历史身份的边界

- 建议引用通过稳定目标 ID 跳回原文，必要摘要只辅助展示；原文被修改、撤回、隐藏或删除时，引用和回顾如何显示必须一并定义，避免后台继续泄露撤回内容。
- 用户已选择撤回只留提示，原文短暂用于重新编辑，不保留长期可恢复历史；建议从未来投递候选中排除。撤回时间限制、短期缓存时长和永久删除行为后续确定，不直接套用社交软件限制。
- 修改头像/名称不应无意改写历史消息；建议快照保存当时身份。头像媒体被删、表情包收藏取消不应随意破坏仍被历史消息引用的原文件。
- 新消息必须有确定保存结果、失败重试与去重；未发送草稿/未完成上传要与已发送消息分开。窗口关闭/多开并发不能丢输入或发出重复消息。具体提交键和失败恢复行为为实现建议，尚未逐项确认。
