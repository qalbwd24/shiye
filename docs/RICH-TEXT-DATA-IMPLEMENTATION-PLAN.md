## 1. 第一步：富文本与文中插图

### 目标

先证明长篇和聊天能稳定显示、编辑/输入及保存同一类图文内容，不先铺开回看和云服务。

### 优先范围

- 基本文本、段落、换行、标题、加粗/斜体/高亮、列表、引用、代码、链接与基本表格；明确 Markdown 扩展和降级规则。
- 图片插在文字中间，保留前后文顺序，支持基础尺寸/对齐与图注；文件 ID 与这次插入位置/时间分开。
- 中文输入法、空格、标点、粘贴、撤销/重做、焦点、缩放记忆；真实输入路径也须通过，不能只验证预制节点。
- 消息显示与长篇阅读采用一致语义；长篇可编辑，聊天归篇/回看投影只读。
- 兼容旧 HTML/Markdown 读取，保留原件；未知内容只读降级，不转换后覆盖。

完整 Word 分页、浮动环绕和非线性分栏不作为第一步默认范围；分栏继续暂缓。最终控件/编辑器方案需在目标环境验证，不能因聊天已有 Tiptap 依赖就直接替换全部长篇编辑器。

### 本阶段产物与放行条件

- 独立开发库中的图文原型、支持矩阵、虚构混合样本。
- 从真实输入到序列化、重开、再渲染，文字/图片位置/格式一致；图片调宽不改原件字节。
- 旧内容只读打开且原数据不改；失败不产生替代空正文。
- 明确哪些字段能原样往返、哪些仅能阅读降级。通过后再确定富文档内容子集。

阶段内可以使用隔离样本/临时保存验证内容结构，不等于已经接入正式库或开放新生产 API。

## 2. 第二步：统一数据结构与基础接口

### 目标

将第一步验证过的图文结构放进稳定的记录模型，打通新数据写入与读取；物理容器选择单独论证，暂不把 SQLite 迁移作为前置条件。

### 范围

- 分类稳定 ID、复用/单独分类、会话归属与默认分类，保留各自含义。
- 时间依据与精度、消息原时间、图片插入时间、保存时间分开；旧数据不造精确时间。
- Document/Record/Asset/JournalPage 的单一权威来源，按五小时空闲归篇，正文只读。
- 后端校验消息来源和修改权限；撤回清理、短期重编辑、新 ID/新时间重发、操作回执与重试。
- 评论按篇汇总，但可精确关联消息/内容块/某次图片出现；保存一次，按篇展示去重。
- 新增统一接口与旧接口只读适配；先用隔离新数据验证，不全库转换旧 Entry 或旧消息。
- 可携带导出/恢复与媒体、分类、消息、评论引用的 ID 映射，避免新格式只会写不会恢复。

### 放行条件

- 旧格式读取保持，新增记录保存/重启/恢复后关系正确。
- 消息不能从日记端直接改；聊天撤回后各视图一致，原评论不自动搬到重发消息。
- 同图不同出现位置不串评论，跨会话局部消息 ID 不撞记录。
- 服务器权限、失败恢复与真实窗口验证通过，不用 schema 的 32 项检查代替接口/生命周期验收。

本阶段只做普通日记/随记及基本评论关系，不实现朝花夕拾的时间查询、自动组评论或定时投递。

## 3. 第三步：朝花夕拾

在前两步通过后接入：

- 按时间规则读取所有符合的历史来源，排序、分页、去重；不复制成新的普通原消息。
- 同时看多个历史周期，支持长篇时间锚点与图片出现位置；不能识别的旧时间保留精度和说明。
- 无引用自动评论最近展示组，有引用只回复该条/该次图片；输入框显示目标并可切换。
- 评论的固定上下文，输入中出现新组/换间隔不串目标；评论不成为下一轮回看来源。
- 仍以篇阅读、标注与定位评论对象；来源撤回不从快照重新暴露原文。

组时间窗、日历边界和通知方式在本阶段结合原型定。云服务器与自有安卓同步另安排，不绑在第一步富文本上。
