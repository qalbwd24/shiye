## 已确认的职责

| 层             | 职责与维护边界                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------ |
| 会话前端       | 在已有会话设置提供后端选择、对应配置与状态；复用普通消息/引用/图片组件，显示后端真实结果         |
| 后端服务       | 注册实际可用的程序/AI适配器，创建独立实例，执行规则/请求，持久化进度和评论；独立于窗口运行       |
| 固定桥与客户端 | 传送类型、实例、绑定及操作身份；处理分页/流式、重试/取消与本地确认；不重写规则或直接改diary.json |
| 规范数据层     | 日记/消息/媒体/评论仍走统一数据服务；会话绑定、分类标签和UI偏好与正文身份分开                    |

前端更新不应覆盖后端状态；后端修改不依赖修改气泡布局。配置定义/校验由后端提供并版本化，前端渲染表单并提交，错误/不支持能力明确展示。没有实现的AI/机器人服务不显示成可用项。

后端代码已在`src/server/conversation-services/registry.mjs`、`host.mjs`与`src/server/routes/conversation-services.mjs`。前端目标位置为独立的`previews/telegram-chat/shiye-conversation-services.js`模块，普通消息组件继续复用；协议类型/版本与适配映射独立维护，原生`ChatJournalBridge.cs`仅接固定动作。这些前端入口本轮尚未实现，前端按实际契约独立联调；交付分别记录版本、hash、能力和未验项。

## 多会话模型与实施顺序

1. **服务实例与绑定**：区分providerId（能力种类）、instanceId（独立规则/进度）、bindingId（与稳定会话ID的连接）。多个会话选择朝花夕拾时，各自创建/选用独立实例，不共用一个全局规则或游标；标题/壁纸/分类不是主键。
2. **后端调度与接口**：先增加服务发现、实例配置/状态、绑定、增量事件和评论提交接口。每个已启用实例随拾页后台恢复，单飞/去重以实例隔离。当前`db.revisit`作为兼容实例保留，迁移不得清空它或重复投递。
3. **传输适配**：桌面桥增加固定的服务发现/绑定/实例请求动作，worker去掉固定会话假设。所有事件、ack/outbox、撤回、回复和源失效都带实例/绑定范围，使用稳定复合身份，不将同一deliveryId误认为另一个实例的消息。
4. **前端会话设置**：由UI负责实际选择器与表单布局；保存后真实绑定到选定实例。重开能读回配置，错误不伪装成成功。后台服务继续独立运行，窗口退托盘/更换外观不改实例进度。
5. **联调和正式切换**：两会话设置不同分类/换日时刻，隔离验证互不影响、重启续推、来源只读、引用/无引用回复、不重复；先保留旧兼容会话和评论，再正式开启新的会话绑定。

以上第1、2步后端与独立测试已完成；第3–5步前端传输/界面/端到端绑定验收待前端执行。字段落盘、固定动作及冲突码已确定在[实际API](CONVERSATION-SERVICES-API.md)，没有任意URL、程序执行或文件路径入口。AI的模型/提示词/上下文细则仍按先前约定后议。

## 不变的来源与评论语义

历史内容只作为来源投射到绑定会话；实例共享原始日记，不复制多份原文。投递身份按实例区分，SourceRef不变。新统一口引用回复所引历史单条/媒体，无引用由输入框的displayedTarget指定最近展示或选定的一组，草稿/发送/重试冻结实例和目标；后端不猜发送时最新组。旧固定房UI当前默认最近单条，仍待前端按最新需求适配，本轮不改它。切换程序、新来信或改规则均不改绑旧评论；原日记按篇聚合并保留单条/媒体位置，评论不参加回看。

解除绑定保留旧消息/评论与原实例归属。重新接入同一实例沿原进度恢复；选择新实例按新实例的初始化规则执行，不悄悄把旧评论转给它。跨设备的稳定会话身份在后续同步契约中统一，不单凭各客户端数字房间号路由。
