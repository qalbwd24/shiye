# 朝花夕拾：统一记录与跨时间评论方案

更新：2026-10-16。状态：讨论稿；无业务代码修改或正式数据迁移。

本文承接 [数据统一调研](DATA-UNIFICATION-RESEARCH-2026-10-16.md)。本轮用户将核心理解调整为“现在回去看到过去的消息，留下今天的评论”，优先于旧方案的“过去向现在重复投递”。另一对话继续处理 UI，本轮只记录需求与技术取舍。

## 最新确认与具体契约

用户已确认评论不作为回看来源；聊天归篇正文只读，只允许在原聊天端撤回/重新编辑，日记侧可加评论。朝花夕拾不引用时自动评论最近展示的一组，引用某条则只回复这一条；输入框须显示正在评论的对象并能切换。此前本稿“只读尚未确认”的描述已由这次指令替代。

具体字段、只读约束、回看上下文、引用优先级、虚构样本和分步适配见 [统一数据契约 v1](UNIFIED-DATA-CONTRACT-V1.md)。当前只有设计与结构检查，不改 UI、运行程序或旧数据。

## 用户明确的方向

- 聊天记录也有分类。可以复用长篇日记已有分类，也可以由用户另设供聊天使用的分类，不强制两边互相隔离。
- 考虑适配后采用新的图文结构；长篇与聊天尽量一致，聊天进入日记时保留所属会话属性及发送、引用等信息。
- 长篇也能进入回看，通过正文时间戳和图片插入时间提供定位；不能只有聊天消息参与。
- “朝花夕拾”希望在一个群聊式空间同时看到多个过去年份/周期相应日期、时刻的记录。例如间隔一年，显示去年、前年、大前年的相应内容。
- 不希望每次重现都复制出一份完整正文。用户能接受少量数据重复，但希望模型合理，原内容与回看关系清楚。
- 调整间隔时不能让以前的回应失去来源和上下文。
- 当前更倾向于回看原内容并留下今天的评论；评论可以从关联的过去记录上看到，显示真正的评论时间。普通聊天回复与回看评论需区分。
- 评论不作为后续“朝花夕拾”的独立回看来源，用户本轮已经确认；原记录仍可展示关联评论。
- 用户名、头像及不同年代身份如何呈现未定。微信用户名/小程序接入的设想随后暂缓，后续移动端倾向自己写安卓客户端；不在本轮接入微信或设计授权流程。
- 必须平衡体验目标与技术可行性。不能把未经原型验证的 schema、编辑器替换、跨端同步、时间识别写成已经可用，也不能为技术省事改变用户的核心体验。

## 需要保留的区别

分类回答“记录属于什么主题”，会话归属回答“从哪个聊天空间产生”。两者独立，例如一篇记录可以分类为“工作学习”，来源为“灵感收集”。同一分类里能同时有长篇与聊天记录。

“统一格式”指相同的图文、媒体、关系和导出契约。单条消息仍需原始发送时间、作者和引用关系，长篇仍需自由编辑和原段落顺序；不为追求同一个 JSON 外形丢掉这些信息。最终字段与粒度尚未选定。

## AI 建议：可变的回看规则，固定的评论来源

回看间隔只决定当前显示哪些原内容，不作为评论的永久目标。评论绑定稳定的日记/消息 ID；细粒度段落定位待富文档能力验证后再加。

虚构例子：2027-10-16 21:00，一年间隔的视图显示 2026、2025、2024 同日相应时段的三条内容。用户对这组内容写下评论：“这几年当时都在准备考试。”

建议只保存一次这条评论，并关联三个明确的来源。它在这三处的评论区都能展示，评论时间仍为 2027-10-16 21:00；统计和导出按同一评论 ID 去重，不当成三次独立发言。

以后间隔改为三个月，当前回看结果可以改变，但评论关联仍指向原来的三条内容。打开这条评论时能查看当时选择的来源组合，不依赖当前间隔，也不动态扩展到后来新增的“同日”记录。

“评论不再参与回看”建议解释为：评论不作为新的独立回看来源，不因此递归产生更多消息；但打开原记录时，仍能看到其历年评论。例如 2028 年回看 2026 年的记录，可以看到 2027 年留下的评论及其真实时间，而不是把评论隐藏掉。这一显示细则仍为 AI 建议。

实现上可以概念性地分为：

| 信息             | 保存内容                               | 作用                   |
| ---------------- | -------------------------------------- | ---------------------- |
| 原始记录         | 图文、分类、原时间、会话归属等         | 唯一内容来源           |
| 当前回看规则     | 时间间隔、时区、范围等                 | 生成当下视图，可调整   |
| 评论             | 今天写的正文、真实时间、关联来源 ID    | 新的个人记录，保存一份 |
| 评论的回看上下文 | 当时选中的来源集合、回看时间与规则版本 | 还原评论在回应哪些内容 |

不要求每次打开、刷新或重现都生成持久“投递消息”。默认可查询原记录形成视图；需要评论时再固定关联上下文。是否保留单独的浏览历史、怎样通知有新回看，属于后续选择。

源 ID 可以防止间隔变化导致关联丢失，但不能保证源内容被编辑/删除后仍还原当时全文。是否保存必要摘要或版本、源块消失后的提示需要另外约定；撤回原文的清理要求继续优先，不以评论快照绕过。初版至少可显示来源已修改或不可用，不伪造完整原样还原能力。

### 直接评论与组合评论

可以分别考虑对单条旧消息/某篇日记评论，或对这次展示的一组旧内容评论。默认按钮与目标范围尚未决定，不能把“发在群聊里”自动解释为每条评论针对整个历史库。

用户提出的“只能看不能回复”，可理解为不向过去伪造新的聊天发言，但允许留下今天的评论。是否完全禁止评论仍是可选体验，不把它误记成已确认的只读产品要求。

## 时间定位：可实施部分与未知部分

- 聊天有明确的发送时间，优先复用，不因回看改写它。
- 长篇的手打时间戳保留原文。可以评估识别已明确格式并形成时间锚点，不能假定所有手打时间都能准确识别；模糊日期保留原文与精度，不强行猜。
- 新图片可记录插入时间，另与拍摄时间、文件修改时间区分。同一张图片被两次插入，插入时间属于各次正文引用，文件本身可以复用。
- 旧图片未记录插入时间时不能事后编造。可按篇目日期回看或由用户补时间，并说明精度。
- 初版可先按消息和整篇日记定位；长篇按多个时间锚点拆成回看片段，须先验证稳定定位及编辑后的兼容，不在后台重写原篇。
- “相应时刻”用时间窗口/游标处理，不能只查时分秒完全相等，否则容易漏记录。窗口多大、休眠后补看范围尚未确定。
- 默认北京，允许跟随系统；按自然年/月还是固定时长、闰日/月末策略都须明确。间隔一年看多个过去年份是用户给出的目标示例，不等于所有日历边界已定。

## 用普通话解释自动归篇

原先消息 M1、M2、M3 连续产生，五小时没有新消息后，这组在日记列表里算一篇。这是原有默认规则；数据已在发送时保存，不等五小时。

自动归篇可以只是给同一批记录增加共同篇目归属：聊天窗口逐条显示，日记里连起来阅读，内容仍来自同一份记录。用户不需要手动再复制一次，进入日记也不要求丢掉会话、原时间和引用。

此前“整理成正文”是 AI 额外提出的独立文章用途，不作为当前必经步骤。用户现已确认聊天归篇正文只读，修改仅从原聊天端撤回/重新编辑；日记侧可以评论。只读规则只针对消息投影，不取消既有长篇原文编辑能力。

## 平衡体验与技术的分步验证建议

| 层级               | 用户体验目标                                           | 可复用基础                                            | 必须验证/尚未完成                                                                             |
| ------------------ | ------------------------------------------------------ | ----------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 第一层：关系先打通 | 同分类看长篇和聊天；原内容在回看中可见；评论能回到来源 | 现有 entry/message/media ID、分类、时间与评论基础     | 统一引用契约、多目标评论、间隔变化不丢关联、撤回与导出。现有单条 replyTo 不等于已有多目标评论 |
| 第二层：图文一致   | 两种入口图片、Markdown、排版和保存一致                 | 既有 Markdown/HTML 和媒体引用，聊天中已有 Tiptap 依赖 | 富文档适配原型、中文 IME、粘贴图片、撤销、移动端、大文档性能与无损导出                        |
| 第三层：细时间定位 | 长篇多个时间点、图片插入时间也参与回看                 | 原消息时间和长篇篇目日期                              | 手打时间识别、稳定块 ID、后期编辑/移动/删除后的锚点处理                                       |
| 第四层：跨端       | 安卓也能写、看、评论；自建服务同步                     | 拾页自有业务接口与本地持久化机制                      | 离线、冲突、身份与鉴权、媒体同步、通知；不复用 Telegram/微信服务                              |

这不是已承诺的开发排期。可以先用隔离样本验证关键关系而不替换现有正文；最终仍向统一内容模型推进，避免临时桥接变成两套永久格式。数据库是否改 SQLite 与富文档是否选 Tiptap 分别论证，不能绑在一起大改。

验收优先覆盖：换回看间隔后旧评论不失联；同评论在多处显示但只保存/导出一次；旧正文不被错误拆分；撤回不从回看或评论摘要重新出现；同图资源在各入口一致；桌面和安卓输入真实操作，而非只有合成样本。

## 待讨论而未锁定

- 分类选择作用于话题默认值、单条消息还是归篇整体；跨分类移动和改默认时历史是否跟随。
- 一组记录的具体划定方式和目标选择器样式；默认范围已确定为无引用评论最近组、有引用只回复单条。
- 评论作为统一记录中的独立类型或关系对象；默认不参加回看，但搜索/统计/导出仍可包含。
- 来源修改后回看最新内容还是保留某个历史版本；可保留多少上下文，怎样遵守撤回规则。
- 头像/用户名、具体安卓技术栈与云端服务仍未确定。

## 2026-10-16 已确认：按篇阅读，评论可标记消息与图片

用户明确区分评论显示单位与具体对象：仍按整篇日记查看，但可以标记到其中一条信息/消息或某张图片；查看评论时注明目标并能定位。整篇入口可留下总体评论；消息/图片引用不能扩展成针对整篇全部内容。数据契约补 CommentTarget 的 pageId、scope、recordId、blockId、occurrenceId，图片按这次出现定位，不只关联共享图片文件。

无引用评论最近回看组、有引用回复单条、聊天归篇正文只读、评论不进回看继续有效。同一评论在本篇命中多个目标时只展示/计数一次。具体标记样式由后续 UI 设计，当前只更新 [统一数据契约](UNIFIED-DATA-CONTRACT-V1.md)、机器草案及虚构样本，不改界面或旧数据。

## 2026-10-16 已确认顺序：富文本 → 数据结构 → 朝花夕拾

用户确认评论精确关联、按篇阅读的方向；要求先确认富文本优化和数据结构优化，再考虑朝花夕拾。完整范围/放行条件见 [三阶段计划](RICH-TEXT-DATA-IMPLEMENTATION-PLAN.md)。第一步独立开发库验证共享富文档、Markdown/中文输入、文中图片及保存往返；第二步接统一模型与基础接口、消息撤回/只读归篇/精确评论；第三步做回看查询与自动组评论。旧数据先不动，不要求现在迁移数据库。
