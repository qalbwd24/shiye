# 拾页与手机的自建服务器同步

## 当前协议

拾页电脑端通过本地 Node 服务访问 WebDAV，不让浏览器直接跨域访问服务器。服务器地址填 WebDAV 根地址，例如：

```text
https://你的域名或IP/diary-dav/
```

同步文件沿用一本日记的格式：

```text
<WebDAV 根>/diary/diary.json
<WebDAV 根>/diary/<媒体文件名>
```

`diary.json` 是一个 JSON 容器，字段为 `json`、`catagory`、`model` 和 `tag`，每个字段的值仍是 JSON 字符串。正文中的稳定 `uuid`、日期、分类、标签、删除状态和媒体文件名都保留，因此原版或私有版安卓客户端可以继续读取。

## 同步动作

- **测试连接**只读取云端 `diary.json` 和引用媒体，不修改任何数据。
- **只从云端合并**把云端版本导入电脑，不上传电脑内容。
- **合并并同步**先拉取云端，再按稳定标识和内容合并；没有冲突才上传合并结果。

## 从手机迁移到电脑，再让手机和电脑共用

第一次使用时，建议在原版安卓“一本日记”里导出一份包含媒体的完整备份，在拾页的“备份与导入”中导入这份备份，检查日记、分类、标签和媒体数量，再点“测试连接”，最后点“合并并同步”。云端为空时，拾页会把这份已经检查过的电脑库作为第一份云端数据；之后原版安卓或私有版 APK 读取同一个 `diary/diary.json` 即可继续同步。

同一份手机备份不要重复导入。电脑新增内容先在本地保存，然后用“合并并同步”上传；手机新增内容则由下一次同步拉取并合并。若出现同一稳定标识的不同内容，上传会暂停并保留两份，处理冲突后再同步。

## 流量和增量策略

原版 APK 的协议没有增量 JSON：每次同步都会完整 GET、完整 PUT `diary.json`，也不发送 ETag、HEAD 或 PROPFIND；媒体则按本地待同步记录上传，上传后只做一次存在性 GET。因此第一次迁移的上行量约为 `diary.json 大小 + 新媒体总大小`，下行量约为 `diary.json 大小` 加上合并所需的媒体下载。

拾页保留这个安卓兼容格式，但在电脑端增加了条件请求和指纹缓存：

- 服务器返回强 ETag 且云端没有变化时，只收到一次 304 响应，不重新下载正文或媒体；本地投影没有变化时也跳过完整 `diary.json` 上传。
- 媒体文件名由内容 SHA-256 生成。已上传媒体会缓存文件名、大小、SHA-256 和 ETag，服务器支持 HEAD 时只读请求头即可复用本地文件；新媒体或内容改变的媒体才上传字节。
- 如果服务器不返回强 ETag，拾页会退回安全路径，不能假定“文件名相同就一定内容相同”；首次同步可能再次读取 `diary.json` 或媒体。
- 文本变化通常只上传新的 `diary.json`；图片、视频未变化时不会重复上传。同步结果会显示媒体上行字节数和是否跳过了日记文件。

这不是把安卓端改成 JSON Patch，也不能让原版手机自动理解桌面端的增量缓存。服务器仍应为 WebDAV `PUT` 返回强 ETag，并保证 `If-Match`／`If-None-Match`，这样手机的全量协议和电脑的节流策略可以安全共存。

兼容原版 Android 的 `diary.json` 是普通 WebDAV 文件，不是端到端加密容器。拾页默认要求在界面勾选“我已了解兼容格式不是端到端加密，允许本次上传”后才会写云端；这只是明确风险，不代表服务器端已经完成加密。若要求服务器无法看到正文和媒体，应先停用兼容上传，另行设计手机与电脑都支持的加密容器。

云端为空时，电脑当前库会作为第一份云端数据上传。电脑库的媒体按文件内容和名称上传，安卓端引用的文件名与 `diary.json` 一致。

## 冲突与回滚

同一稳定 UUID 的正文、日期、分类、标签、状态或附件不一致时，拾页会保留云端原始 JSON 和本地两份日记，并停止本次上传。打开“冲突管理”选择保留版本或另存标题，再次同步。

每次云端拉取都会在 `data/originals` 中保存原始 `diary.json`。云同步不是历史备份，仍应定期创建 `.syvault2` 加密备份。同步前建议暂停手机和电脑编辑；首次测试只使用一篇虚构日记和一个小媒体文件。

密码只存在当前同步请求中，`data/diary.json` 只保存地址、用户名、远端哈希和时间。公网 WebDAV 必须使用 HTTPS；服务器端应先完成专用目录和认证，再把真实日记接入。
