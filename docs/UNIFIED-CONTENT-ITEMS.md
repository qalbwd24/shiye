## 用户已确认的方向

- 长文依手打时间戳切成类似消息的内容单元，聊天直接使用同一种格式。
- 图片一般不另打时间戳，优先采用该次图片插入时间；视频沿相同规则。不能用资源首次入库或EXIF拍摄时间冒充插入时刻。
- 每条单元包含自己的时间、正文、可选回复和评论关联；支持文字、图片、视频及图文混排。
- 原图片/视频资源继续单独保存，正文以资源引用确定位置；“原文件链接”是可选显示方式，不是从源数据删除媒体。
- 旧日记要纳入相同模型，保持旧原件和独立转换副本；不能因格式不支持而丢掉原文、样式、换行或附件。
- 沿用此前：归篇按会话空闲间隔，聊天归篇只读；撤回后只留提示，重发用新ID/新时刻；评论可定位消息/块/某次媒体出现，按篇汇总，评论不进入普通回看。

## 消息为主体的约束

- Message/Record是内容主体，id全库唯一且与时间、日记名、会话名、分类名分离。一条消息可有多段文字和多个媒体节点；同一时间戳不构成唯一约束。
- 日记名称通过journalPageId关联的元数据提供，会话通过conversationId关联，分类通过categoryId关联；对外读取可以展开名称作为消息属性。归属对象负责名称/排列等元数据，不另存一份可独立编辑正文。
- 长文是按原顺序组合消息的视图；聊天是按会话组织消息的视图。消息无需因换入口或回看而复制正文，编辑权限仍依据来源判断。
- 无回复的消息replyTo=null。评论正文仍共用相同内容格式，通过commentOn绑定原消息/媒体出现或篇；既有按篇汇总规则保留。

## 长文自动处理的提交链（实现建议）

富文本树解析 → 识别正文时间锚点 → 确定文字区间和媒体出现 → 分配/匹配稳定消息ID → 验证共同结构及原文往返 → 原子保存消息与原文顺序。

新长文沿用既有自动保存节奏，中文组词完成后取得一致快照。准备工作不改变原文，提交时校验源revision，不能把过期切分覆盖用户新输入；不要求在UI中显示切分边界，不重新弹“发送消息”步骤。

每次编辑增量匹配原消息/块身份：仅新增内容分配新ID，原时间不因改名或保存刷新；真正拆分/合并记录映射，已被评论/引用的旧身份不得静默改绑。不能按全篇消息下标或完整文本哈希每次重新生成ID。

切分后的消息可以按时间查询，长文重组仍遵循原文顺序与排版信息。放行必须验证文本/空白/格式/媒体出现/标题及分类属性保真、保存重开、撤销、评论定位及导出恢复。历史未知时间按已确认的内容编辑时间规则兜底并保存依据；缺失或冲突条目另列，不自动填迁移时刻。

## 共同结构（建议）

长文切出的记录和聊天记录都使用同一Record字段及同一richdoc正文，不长期维持“聊天Markdown权威、长文richdoc权威”两套持久正文。Markdown是输入/导出的一种表达，聊天输入发送时转换成共同正文。

| 字段                  | 责任                                                                      |
| --------------------- | ------------------------------------------------------------------------- |
| id                    | 全库稳定记录ID，不从时间、排序下标或正文哈希临时生成                      |
| kind                  | diary / message / comment；区分业务来源，不改变body格式                   |
| body                  | 共用图文结构，可依次含文字、image、video等节点；撤回为null                |
| eventTime             | instant（UTC）、timeZone、precision、source；区分明确、推定、编辑时间兜底 |
| createdAt / updatedAt | 系统创建/修改时刻，不替换eventTime                                        |
| origin                | 来源入口、原entry/page、会话、旧来源身份和转换映射                        |
| categoryId / tags     | 实时可变属性；更新不改变原内容时间                                        |
| replyTo               | 可选普通引用回复目标，使用稳定记录/块/媒体出现身份                        |
| commentOn             | 评论的目标引用集合，可为篇、单元、块、媒体出现或固定回看组                |
| state / revision      | 有效、撤回、删除及并发同步版本                                            |

没有回复的长文单元replyTo=null；聊天无引用的消息同样为null。评论正文仍是同格式Record，通过kind/commentOn体现用途。评论单独保存一次，不在每条源记录里复制整份评论数组；按篇汇总时去重。

JournalPage按原文顺序引用Record，Conversation按消息序列引用Record。归篇和回看展示只引用原Record，不建立另一个可独立编辑的消息正文。长文编辑器操作对应记录/块；一次提交原子保存受影响记录、顺序、版本和派生索引。旧原件仅作为保留来源/迁移回退，不能形成另一份同时可编辑的真源。

这是下一版存储适配目标；当前body/Record接口尚未变更。是否沿用物理JSON容器不影响共同契约，不把换数据库作为前置任务。

## 时间与拆分

1. 文字：完整手打时间标记开启时间区间，其后文字直到下个标记沿用该时间；不为每个自然段发明单独写作时刻。同一时间可有多条内容。
2. 新媒体：该次出现的insertedAt作为它的内容时间，独立于asset首次登记时间；图片和视频一致。重复使用同一资源可有不同出现ID及插入时间，重试/移动/排版不重设已记录时间。
3. 图文混排：body允许混合节点，但不能为凑成一条而抹掉真实时间差。聊天中一次发送的文字和附件是一条消息，主时间为sentAt，媒体可另保留插入信息。长文中某个媒体与文字时间不同，可拆成相邻单元并保留共同分组/原位置；只有明确属于同次事件时才共用一条主时间。自动合并关系属于实现建议，不擅自通过相邻距离推断语义归属。
4. 文字无明确时间：沿用已确认的原内容编辑时间兜底，标明edit-fallback；属性修改和本次迁移时间不能当成内容时刻。
5. 原文顺序与时间顺序分别保留。今天向旧篇补图会有今天的插入时间；长文仍放在用户插入的位置，回看按事件时间排列。时间倒序不重写原文、也不自动推成第二天。
6. 时间只是排序/查询字段，ID才是引用和评论身份；时间精度保留分钟/秒等，不能把推定或补零伪装为更高精度。

手打时间戳原文保留；解析只生成结构/关联，避免删除用户特意输入的标记、空行或分割线。代码、引用中的日期不当作用户新的写作标记。HTML/Markdown先正确解析再切分，不用正则直接剥掉图片/标签后截字符串。

## 旧媒体：能适配结构，不保证恢复失去的事实

已知：当前旧附件无可靠的每次插入时间；旧源/媒体中若有明确逐次字段可读取为依据，但文件修改时间、拍摄EXIF、importedAt均不自动等价。新富文档已登记的insertedAt可直接保留。

用户已确认：旧日记附件是独立附件，没有所属文字段，缺少真实插入时间时统一按所属日记原内容编辑时间安排回看，source=edit-fallback，并保存sourceField。真实insertedAt仍为null。不再执行“跟随所在文字段”的旧媒体推定。

同篇多个旧附件可以共享兜底时刻，但各有独立出现ID，按原附件顺序排列，不能按时间去重。原内容编辑时间也缺失或存在不同来源冲突时单列异常，不用迁移时刻填充。新图片/视频仍以实际插入时间为准。

## 回复、评论与编辑身份

- 普通replyTo引用一条源内容；评论用commentOn明确“篇/单元/块/媒体出现”。同图多次出现不能只按assetId定位。
- 日记页面按篇显示评论；精确指向单元或媒体的评论标明来源位置。
- 朝花夕拾中显式引用优先指向该条；不引用默认最近展示的一组；开始输入固定目标集合，后续切换时间规则不改旧评论关联。
- 修改一个旧段落不能把全篇所有单元换ID。拆分/合并须保存来源映射，旧引用保留已绑定来源与必要版本信息，不能把字符串偏移当永久ID。算法升级也不能随意重分配旧单元身份。
- 聊天撤回以原ID留墓碑，清理源内容和派生缓存/搜索/引用；重发新ID/新时刻，原评论仍指向旧墓碑，不自动搬到新消息。评论不作为普通回看来源。

## 适配与放行

1. 先定义共同Record/时间/关联校验和虚构往返样本；在隔离库接新长文/聊天共同写入。
2. 长文解析→时间分段→媒体独立时间→稳定身份映射→共同Record候选＋原顺序清单。先做实际编辑/保存/重开/撤销/同步/导出恢复验证。
3. 旧篇只读生成新候选：先覆盖用户十月写法，再覆盖全库。核对原文字、换行、样式、媒体个数/顺序、时间依据、ID稳定和评论目标；异常另列复核。
4. 表格/列表/折叠/音频/文件等复杂旧内容不能硬切后丢结构。共同body尚不支持的节点保留原文兼容入口及来源引用，扩格式/单独适配后才放行，不声称现有richdoc v1已无损支持所有内容。
5. 统一读取满足主窗、快捷窗、聊天、导出后，再接朝花夕拾查询与展示；切换正式库作为单独可核对步骤。旧原件不覆盖。
