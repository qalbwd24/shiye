## 1. 本轮已经确定的产品规则

1. 长篇与聊天共用图文内容、分类和媒体规则，聊天保留会话归属、发送时间、引用等信息。分类可以复用既有分类或由用户另建。
2. 聊天按每会话默认连续五小时没有新消息归篇，间隔可调；消息发送即保存。归篇正文只读，不允许在主窗或快捷写作中另改一份。
3. 修改消息从聊天端撤回、重新编辑处理；撤回只长期留提示，原文只短暂用于重新编辑。撤回后的更新要同步反映到归篇、回看、搜索和引用。
4. 归篇正文可以留下评论。评论也采用共同图文结构，但不作为“朝花夕拾”的独立回看来源。
5. 朝花夕拾按时间规则把符合条件的原消息/日记片段呈现在一个群聊式会话，保留原来源；不为每次重现复制完整原文。
6. 用户已选择并补充：**不引用时自动评论最近展示的一组旧记录；引用某条时只回复这一条。** 输入框显示正在评论的对象，并能切换。不是要求每次手动选择，不默认保存为无关联的今天随记。
7. 回看规则可以改变，既有评论绑定的来源集合不能跟着重新计算。头像/用户名、安卓技术栈和更细的时间边界尚未选定。
8. 旧数据先不动。本轮先定接口与模型，结合已有代码分步适配。不同入口实现同一契约，不要求本轮更换数据库或全部编辑器。

后文除以上规则和代码现状外，具体字段、接口、TTL、算法均是 AI 设计建议，实施前允许调整。

## 2. 核心关系

```text
Category ← Record → Conversation
              │
              ├─ body：同一套图文结构 → Asset
              ├─ eventTime：原时间；图片位置有各自 insertedAt
              └─ commentOn → 固定的一条/多条 SourceRef

JournalPage → 按顺序引用 Record
  长篇：一条文档记录，可在写作入口编辑
  聊天归篇：多条消息记录，正文由它们生成，只读

朝花夕拾时间查询 → 临时展示回看组
开始输入 → 固定该组引用
发送评论 → 保存 Comment Record + RevisitContext
```

同一条原记录在聊天、日记、回看中有不同展示方式，但正文只保存一份。`JournalPage` 是日记列表中的“篇”，不另保存可编辑消息副本；旧 HTML 可作为带来源版本的阅读缓存。

## 3. 对象与字段

快捷长文接入先遵守 [继承与数据适配基线](QUICK-RICHDOC-INHERITANCE.md)。用户手打时间保持原样，不等同每次保存时间。图片出现的 insertedAt、媒体 importedAt/文件修改/拍摄时间分开；旧图片无插入时刻保持未知。按独立手打时间行建立段落锚点、缺时区按日记时区推定、图片跟随段落回看等属于后续 AI 实施建议，尚未确认规则/新增节点或实现解析；不借本次审计修改机器 schema 或旧数据。

### 3.1 分类 Category

| 字段      | 含义                                                   |
| --------- | ------------------------------------------------------ |
| `id`      | 稳定分类 ID，改名不改 ID                               |
| `name`    | 用户看到的名称                                         |
| `pickers` | 建议为 diary/chat 选择器的可选范围；这不是内容访问权限 |
| `order`   | 手动顺序                                               |

同一个分类 ID 可供两边使用。“单独分类”建议仍放同一分类表，按选择器范围控制是否常用；归篇后的分类仍可在日记列表显示，不能因为它仅供聊天新建选择就隐藏已有日记。

v1 每条内容保留一个主分类，与当前单分类模型相容，标签可后加。会话的默认分类仅影响之后的新消息，不自动改变历史；归篇保存分类快照，分类改变时下一消息另起篇，继续现有行为。单条跨分类移动、改归篇分类和历史重分规则仍待定，不让“正文只读”意外禁止合法的分类管理。

旧分类目前是名称字符串。未来用独立映射关联名称与新 ID，读取适配不回写旧条目；改名/合并须原子更新相关映射和会话默认值。不能一启动就给所有旧记录加字段。

### 3.2 会话 Conversation

`id, name, kind=journal|revisit, defaultCategoryId, idleSeconds`。

- 普通随记为 journal；朝花夕拾为 revisit。二者可共用消息列表外观，写入行为由会话类型决定。
- 分类与会话是独立关系：相同分类可以包含多个会话及长篇。
- `idleSeconds` 建议使用整秒，现有 5 小时映射为 18000；保留现有允许区间的换算，不把 UI 显示单位与存储绑死。
- 现有来源 UUID + roomId 是适配层身份，新契约中会话 ID 不直接采用 Telegram 对象作为公开格式。

### 3.3 统一内容 Record

共同字段：

| 字段                   | 含义                                                          |
| ---------------------- | ------------------------------------------------------------- |
| `id`                   | 全库稳定 ID，不随分篇/回看/分类变化                           |
| `kind`                 | diary / message / comment                                     |
| `title`                | 长篇标题；消息/评论为 null，聊天归篇标题由会话和日期生成      |
| `categoryId`           | 主分类；评论可用 null 表示不额外分类                          |
| `origin`               | 产生入口 kind=diary/chat/revisit、conversationId 以及适配身份 |
| `body`                 | 同一 Document；撤回后必须为 null                              |
| `eventTime`            | 内容对应的时间、精度、时区和依据                              |
| `createdAt, updatedAt` | 真正保存/修改时间，UTC，不替代原时间                          |
| `revision`             | 并发与同步版本                                                |
| `visibility`           | hidden / draft；配合状态过滤，回看不暴露隐藏/草稿             |
| `state, withdrawnAt`   | active / withdrawn / deleted；撤回时刻                        |
| `replyTo`              | 普通消息引用目标；与评论目标分开                              |
| `supersedesId`         | 建议用于重发后关联已撤回的旧消息，不保存旧正文                |
| `commentOn`            | 评论的 CommentTarget 集合、contextId、group/single 模式       |

回看来源与普通消息引用使用 `SourceRef={recordId, blockId:null|稳定块ID, observedRevision:null|版本}`；评论另使用下节 CommentTarget。来源默认按整条消息/整篇记录关联；稳定块支持后才能开放细段引用，不用字符串偏移冒充稳定定位。observedRevision 只说明当时看到哪个版本，不保证系统已经保存该版全文。

评论与原内容使用同一正文格式。评论通过关系查询回原记录，不复制到每篇 `comments[]` 里；对三个来源的一条评论保存一次，在三处都能看到，统计/导出按评论 ID 去重。

当前日期选到哪天、实际写作时间和内容发生时间可以不同。`eventTime` 包含 `instant`、`local`、`timeZone`、`precision` 和 `source`；旧记录不确定时保留 local/精度，instant 可为空，不擅自造准确秒级时刻。

回看资格由服务端规则决定：active 且 kind 为 diary/message，再经过范围/隐藏/草稿过滤。comment 永远排除。客户端不能传一个 `recallEligible:true` 把评论重新纳入回看。

### 评论的阅读单位与精确标记

用户最新明确：仍以整篇日记为单位看内容与评论，但评论可以针对整篇、其中一条消息或某次图片出现；查看评论时标注目标并可以定位。不能用“评论出现在这一篇”推断它针对整篇所有内容。

回看查询/消息引用继续使用 SourceRef；评论改用更明确的 CommentTarget：

```json
{
  "pageId": "page-chat-2026",
  "scope": "image",
  "recordId": "record-message-2026",
  "blockId": "block-message-image",
  "occurrenceId": "occurrence-message-image",
  "observedRevision": 1
}
```

| scope  | 精确含义                               | 必须保留的定位                             |
| ------ | -------------------------------------- | ------------------------------------------ |
| page   | 针对整篇的总体评论                     | pageId；其余内容位置为空                   |
| record | 针对该篇中的一条消息/文档记录          | pageId + recordId                          |
| block  | 针对长篇内部一个内容块（后续适配能力） | pageId + recordId + blockId                |
| image  | 针对正文/消息里的这一次图片出现        | pageId + recordId + blockId + occurrenceId |

pageId 负责“在哪篇汇总查看”，scope 与内容 ID 负责“具体回应哪里”。assetId 只代表文件，不是图片评论目标；同一图片文件在两篇或同篇两次出现，评论不能因文件复用自动串过去。旧附件暂时没有可靠出现位置时，不编造精准锚点；保留整篇/消息定位或待适配层提供经验证的出现位置。

**整篇阅读：** 打开一篇时显示正文与本篇全部关联评论，注明“针对整篇/某条消息/某张图片”。点击评论中的来源标记，在这篇内滚动定位并短暂高亮相应消息或图片；从图片/消息上的评论标记也可反向定位到评论。标记和高亮使用显示层，不写进原正文。侧栏/底部等具体布局由 UI 后续决定。

同一组评论可能回应一篇内多条消息：该篇评论列表只显示一张评论卡，卡内列出本篇命中的多个目标；跨篇关联时各篇可见同一评论，仍只保存/计数一次。查询返回本篇 matchedTargets，评论的完整上下文可另外展开，不把其他篇的隐藏内容顺带暴露。

**既有默认继续适用：** 不引用时关联最近回看组中实际出现的那些消息/片段/图片，并记录它们各自 pageId；不能扩大成这些篇内所有未展示内容。引用单条消息时只标记那条消息，引用图片时只标记该次图片出现。打开日记的总体评论入口才使用 scope=page。评论不作为独立回看来源。

源消息撤回、图片从正文移除或旧块不存在时，保留原目标身份并显示“来源已撤回/位置已不存在”，不自动改挂同文件的另一张图或相似段落，也不恢复已撤回正文。v1 已归篇成员不自动重分；以后要重分篇目，必须另行设计历史归属/别名映射，不能删除旧 pageId 使评论失联。

### 3.4 Document 与媒体

候选 `Document={format:"shiye-richdoc",version:1,content:[Node...]}`。节点采用接近 ProseMirror 的 type/content/marks 形式，但由拾页明确节点契约和版本，不能直接无条件接受任意编辑器插件对象。

v1 设计覆盖 text、paragraph、heading、列表/任务、blockquote、codeBlock、table、horizontalRule、image/video/audio/file、timeMarker；未知历史节点只能走保留/只读降级，不能静默丢弃。结构 schema 先校验形状，具体节点嵌套、表格和插件语义还需编辑器适配验证，不宣称已实现“任意 Markdown 无损往返”。

图片出现位置保存 `blockId, assetId, occurrenceId, insertedAt, widthRatio, align, caption, alt`：

- `assetId` 指文件，`occurrenceId` 指这次插入；同图插两处可有不同插入时间/尺寸。
- 图在正文序列中的位置决定前后文；附件文件独立存储不会妨碍文中插图。
- `insertedAt` 是插入事件，不自动等同 EXIF 拍摄时间或文件修改时间；旧图没有时刻就为空。
- Asset 保存 ID、MIME、原名、大小、哈希及不含绝对路径的 blobRef。当前 `media/id` 可以原位复用，原件与缩略图的关系逐步扩展。
- 所有正文、引用节点、头像等资源引用都参与可达性检查，不能撤回一条消息就删掉仍被别处使用的文件。

正文 Markdown 原始输入可另保存在受控来源字段或旧记录中，不能与富文档同时作为两份可独立编辑的权威内容。撤回时这些来源、HTML 缓存、搜索索引和历史中的原文都须清理，不能把原文藏进“来源字段”。

### 3.5 日记篇目 JournalPage

共同字段：`id, kind, categoryId, conversationId, recordIds, bodyPolicy`。

- `kind=diary`：通常引用一个 diary Record，bodyPolicy=document-editable；不影响原有长篇写作。
- `kind=chat-segment`：有序引用多个 message Record，bodyPolicy=derived-read-only；附 `grouping={idleSeconds,firstAt,lastAt,state}`。
- 归篇内容从消息动态生成或使用可重建缓存。消息撤回后显示撤回提示，评论不会改写原消息。
- 不把 comment 放入 `recordIds`，避免评论延长五小时窗口或变成历史原文；通过关联查询显示。
- “五小时无新消息”和“30分钟显示时间分隔”不混用。

正文只读不靠传入的 bodyPolicy 获得权限。后端依据篇目来源与消息类型独立拒绝直接改写；客户端的只读标识只是提示。

## 4. 朝花夕拾查询与自动评论的准确含义

### 4.1 从日记筛选来源

候选接口 `POST /api/unified/v1/revisit/query`：接收 conversationId、ruleRevision、显示时间窗 `[from,to)`、分页 cursor，返回有序回看组。

规则 `RevisitRule` 保存间隔种类（日历/固定时长）、单位与步长、IANA 时区、分类/会话/内容类型范围、分组窗口和无效日期策略。规则改变提高 revision。暂不锁定“组”是 1 分钟、5 分钟还是另一个时段；示例的 60 秒仅为虚构验收条件，不是用户确认默认。

对每个符合规则的历史来源，计算它在本次回看轴上对应的时刻，保留原 eventTime 与 `replayAt`。间隔一年时，对匹配窗纳入所有符合的过去年份，不只是去年。按 replayAt、原时间、稳定序号/ID 排序；标识和 20 位旧消息 ID 按字符串/BigInt 处理，不用 Number 造成精度丢失。

消息正文、日记正文和图片锚点不能同时作为三个重复来源。按稳定 source key 去重：图片已包含在该回看片段时不另投一条；只有明确独立时间锚点的出现位置才可独立呈现。旧长篇先按整篇日期读取，篇内锚点通过隔离验证后开放，不修改旧正文。

分页必须说明组是否完整；自动评论关联整个组，而不是第一页刚加载的几条。大组允许分批渲染，但必须有完整成员清单/服务端组句柄，不能静默漏掉未加载记录。

回看组是显示原记录的投影，不新增原消息。内部可以使用虚拟消息 ID 呈现，但不经过普通聊天新增消息/自动归档管道，否则会重复入库并递归回看。

### 4.2 用户直接发送：自动评论最近展示的一组

建议适配层维护 `presentedContextId`，表示**确实已展示的最近完整回看组**，不能仅用“服务端最近查到的一组”。UI 不需要让用户每次选；但必须能显示当前关联范围，避免盲发。

候选交互与提交规则：

1. 第一次开始输入/粘贴/加图片时，固定当前组为本草稿的 composeContextId。
2. 后面新组到来、规则变化、滚动加载都不偷偷改变已写草稿的目标；清空/发送或主动换目标后再取新组。
3. 发送时提交 operationId、composeContextId、该组展示版本、正文、expectedSourceRevisions；服务端验证组属于当前回看会话，成员仍可评论。
4. 默认目标是固定组的全部来源；用户引用某条时覆盖为 single，只关联这一条。用户已确认输入框应显示当前评论对象，并可切换；具体控件由后续 UI 任务实现。
5. 尚未展示任何组时保留草稿并说明还没有可关联记录，不自动挂当天全部日记或一个空目标。
6. 目标中有来源刚撤回/删除或内容版本变化时返回 context-changed，保留草稿并提供确认当前来源的流程；不悄悄改变目标集合后发送。

“开始输入即固定”“空组如何提示”和冲突流程为 AI 建议，用户明确确认的是默认自动评论最近展示的组。

### 评论对象提示与切换（确认目标，控件为候选）

输入框必须显示实际将关联的对象。组模式可以是“评论：10月16日21:00 · 2026/2025/2024 · 3条”；单条模式可以是“回复：2025年的某条记录”。这些文案只作示例，年份/数量取真实目标集合。

建议点击该提示打开目标选择：最近一组、其他已展示回看组、某条原记录。切换只改变关联，不清空文字、图片或草稿。引用消息立即切为 single；取消引用建议回到本草稿原先固定的组，主动点“最近一组”才切到最新组。发送成功/清空草稿后再跟随新的最近组。

服务器提交 group/single 的明确目标，不按发送时的当前墙钟时间重算。草稿如需重启恢复，正文和目标引用一并恢复；组句柄过期不能无提示换目标。输入法正在组词时不由目标选择器截获组词按键。

### 4.3 保存回看上下文

`RevisitContext={id,conversationId,ruleId,ruleRevision,ruleSnapshot,groupKey,displayWindow,seenAt,sources:[SourceRef...]}`。

浏览时可只持有临时组句柄；成功评论时再持久保存组清单与规则快照，不每次刷新复制原文。服务端需提供句柄过期后的重新解析/草稿保留，不把临时内存 ID 当作重启后有效的永久关系。

评论的 `commentOn.contextId` 指向上下文，`targets` 保存 CommentTarget。group 模式的精确内容引用须逐一对应完整来源集合，并附各自 pageId；single 模式可指向其中一条来源，或该来源内明确引用的图片/块。不能由一条消息的引用扩大为整篇评论。规则以后更改不重算旧评论目标；删除规则或会话不级联删除评论，至少保留上下文元数据。

例如 2027 年评论了 2026/2025/2024 三条：评论真实时间是 2027，三处都能查到同一评论；2028 再看 2026 原记录，可带出这条评论，但不把 2027 评论作为另一个独立回看源。来源被撤回时显示不可用/撤回状态，不能靠上下文快照恢复原文。

## 5. 撤回、重编辑与正文只读

### 写入能力矩阵

| 内容                   | 写作正文直接修改           | 聊天原位直接改字 | 聊天撤回/重新编辑        | 加评论               |
| ---------------------- | -------------------------- | ---------------- | ------------------------ | -------------------- |
| 长篇日记原文           | 原能力继续保留             | 不适用           | 不适用                   | 可                   |
| 聊天消息及其归篇       | 拒绝                       | v1 不提供        | 可                       | 可                   |
| 朝花夕拾中的原记录投影 | 拒绝                       | 拒绝             | 可跳回原聊天处理         | 可，默认本组         |
| 评论                   | 编辑规则另议，不借机改原文 | 编辑规则另议     | 不自动套用原消息撤回策略 | 可支持回复关系，后议 |

撤回建议用带 operationId 与 expectedRevision 的命令。所有归篇只是关联，不需要把修改复制到另一正文。服务端提交撤回状态，原消息 ID 留为墓碑；当前正文、缓存、引用预览、搜索、历史和桥接副本中原文都清理，资源仅在无其他引用且符合保留策略时回收。

短期重新编辑建议只用本地内存缓冲并设置 TTL，具体时长未定；不写永久 history/日志/备份。用户已确认重发作为新消息，采用新的消息 ID 与新的发送时间，旧评论保留原关联。建议另用 supersedesId 关联旧墓碑；这个辅助字段仍为实现建议，不恢复旧正文。

离线撤回需要操作队列、幂等回执和墓碑优先：延迟到达的旧 create 不能使消息复活。已有归档回执只证明旧消息曾被接收，不代表最新状态已同步。撤回之前已经生成的独立备份与导出不可能仅靠更新在线库改写；恢复合并时也须尊重更新的墓碑。

历史旧归篇若已被用户人工改写，仍视为旧内容，保留现有保护，不因本次只读规则回写它。新协议归篇默认执行强制只读；旧数据何时接管是后续显式任务。

## 8. 不变量与验证边界

机器 schema 校验字段、枚举、必要条件、撤回正文为空等；样本关系校验另外验证 ID 唯一、引用存在、分组成员、评论目标、资源引用、时间顺序和禁止评论作为来源。它不证明编辑器实际渲染、数据量性能、服务器权限或撤回完整清理已实现。

必须覆盖的反例：不同会话同消息局部 ID；分类改名不改来源；组分页不完整；评论目标跟着规则变化；评论进入回看；撤回消息仍有 body；迟到 create 复活墓碑；归篇引用评论或跨会话消息；图片重复 ID/丢失；从旧备份恢复后关系错位。

格式采用 [JSON Schema Draft-07](https://json-schema.org/draft-07)，以复用本工作区已有 Ajv 6 检查器，不安装新依赖。只用本地 schema 的内部引用；schema 标识 URI 不要求联网。参考 [JSON Schema 结构与引用](https://json-schema.org/understanding-json-schema/structuring)。

## 9. 导出与恢复的关系规则

完整可恢复包包含上述对象图及实际媒体文件、清单与哈希。正文图片顺序、SourceRef、commentOn、supersedesId、页成员和规则快照均须保留。当前虚构示例只有字段图，不含文件，不能拿它当完整恢复格式已验证。

恢复先分配/核对分类、会话、资源、记录、篇目和上下文 ID，再一次性重建引用；同一评论被三处查看仍只导出一份。遇到 ID 冲突比较版本与内容，不盲目重编号后遗漏关系，也不复活已撤回正文。

Markdown/HTML/PDF/DOCX 阅读导出按篇目顺序生成，消息带原时间和会话来源，评论放独立评论区域，显示真实评论时间。阅读导出不赋予消息正文新的编辑权威；外部改好的文稿不能作为普通保存覆盖原消息。

范围导出若没包含被引用来源，需要明示缺失关系或显式补带依赖；不能为了闭合引用偷偷扩大全库导出。外部引用占位的精确包格式在实现导出时再补，不宣称本次闭合样本已经覆盖范围导出。撤回/隐藏/草稿及评论关联可见性检查由同一业务层执行。
