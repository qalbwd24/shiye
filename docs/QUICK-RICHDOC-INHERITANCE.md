## 六、编辑器接入点与当前缺口

现有 `body-editor` 的对外合同包括 `render`、`command`、`insertDateTime`、`focus`、`atStart`、`commit`、`syncIdentity`、`capturePosition`/`restorePosition`、`newDocument`、源码/原文控制及清理。窗口层复用这些能力，不应复制一套保存/托盘流程。

`createRichEditor` 当前只提供 checkBody/getBody/setBody/parseMarkdown/insertMarkdown/getMarkdown/destroy 和底层 editor。这是内容原型，**不能当作兼容 body-editor 的替代件直接装入**。

| 已核对差异                                                               | 后续适配                                                                             |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| 时间命令/智能段末换行/段落缩进/标题往返没有接原公共合同                  | 用新编辑器事务承载旧语义，补旧用例到新文档结构，保留 IME 和一次撤销                  |
| 独立 IDB 草稿没有 Entry ID/分类、服务端身份重绑、统一保存和 native close | 实现文档适配器，接持久化/冲突/关闭协议，不复制试验页定时器进正式窗                   |
| 新图片直接插入，未复用图片确认对话框；临时 Blob/哈希 ID                  | 接既有媒体流程和稳定引用，并维护异步原光标/篇目身份                                  |
| 当前字比例 60%–200%、预览双栏和整排工具栏                                | 使用正式快捷窗范围/偏好/布局，不把试验 UI 带入常用入口                               |
| prepareRichMarkdown 会按日记约定预处理新输入分割线                       | 与旧内容读取/显式导入区分；旧 Markdown Setext 标题和原件不能在读取时被全篇改造成横线 |
| 图文 JSON 与媒体原件能往返，但旧端备份/恢复/同步未接                     | 完成 D02–D08 后，才称为数据接入；旧端不能支持的布局应说明降级并保护权威原件          |

## 七、验收放行顺序

1. 四核心：新建快捷测试篇 → 时间戳 → 中文长文/连续回车 → 分割线 → 粘图确认/取消 → 文中预览与续写 → 一次撤销/重做。与旧行为逐项对照。
2. 生命周期：先标题停到自动保存，再写正文/插图；正文先写；标题正文交替；保存/读库/隐藏/唤回/上一下一篇/主窗同篇一致；失败保留输入，空白不建篇。
3. 多窗/偏好：同篇分叉提示；旧比例窗最后关闭；分类管理返回；设置/主题/字体/留白；真实中文候选、物理热键和目标多屏/DPI。
4. 数据：重启读取 → 新旧混合库 → 原件/完整备份恢复到另一隔离目录 → 媒体哈希与 ID 映射 → 主窗/聊天投影的只读与来源一致。未知格式不覆盖，旧篇不批量变动。

每项记录原编辑器基线、新编辑器结果、正文/格式/图像原件/定位/版本/保存状态证据。旧测试只证明旧路径仍通过，新侧结果当前都不能填写为已通过。既有未完成的真实 IME/物理热键/混合 DPI 验收仍须标为未验收，不能因“继承”自动变成成功。

## 八、用户追问：手打时间与图片时间

用户长文的可见时间戳仍由自己手动输入/触发快捷键。本轮确认时间来源必须拆开，**不是以最后保存时间替换正文表达时间**。当前代码：新试验页本地文件插入图片时，在图片节点写 `insertedAt=new Date().toISOString()`、独立 occurrenceId；正式旧媒体的 importedAt、lastModified、EXIF 字段不能证明某次文中插入时刻。新时间锚点识别和回看计算尚未实现。

| ID  | 必须保留的时间边界                                                  | 验收/数据含义                                                                                                                |
| --- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| T01 | 手打/快捷键时间保留原文；日记日期、保存时间不覆盖用户写出的时间     | 不强制自动插可见时间，不把一篇所有段落统一归为最后编辑时刻；为后续多个时间锚点留位置，但不猜全文含义                         |
| T02 | 图片每次出现的插入时间与文件拍摄/修改/上传时间、篇目时间分开        | 新文件插入自动写隐藏 UTC insertedAt，显示可用北京/系统时区；同图可有多次出现。旧图未记录时用未知，不以导入或当前保存时间补造 |
| T03 | 时间精度和依据必须保留，历史缺日期/时区或内容歧义不得变成伪精确时间 | 仅有日期不能冒充秒级；只写时分不无提示补日期；推定与明确标识区分。图片缺时间不影响原图/正文读取                              |

以下为 **AI 建议，未当成已确认或已实现**：

- 优先识别正文独立时间行的明确手打时间，形成不改原文的时间锚点。其后普通文字可继承最近有效锚点，直到下一锚点；图片也能关联所在文字段，但这只是内容关联，不覆盖图片真实 insertedAt。
- 后续用户已明确无时间戳日记按编辑时间兜底，替代此前“用户选定日期”的 AI 建议；必须标明修改时间来源，不能将整篇修改时间冒充逐段写作时刻。首个锚点前的内容、仅时分等仍待补规则。代码块、引用中的示例时间或句中提及的往事不自动当新时间段。编辑/删除时间行时重算关联，但不能改掉原图的插入事实。
- 历史完整日期时间未写时区时，可建议按用户选定的日记时区（缺省北京）解释，但应标明推定来源；无法确定的值留待确认，不因 VPN 或当前系统时区变化重写历史。
- 后续用原快捷键插时间时，可在保留原可见格式的同时附加结构化锚点；完全手敲的旧文字仍通过明确规则读取。这不能理解为新增长篇自动打点功能。
- 原图片移动、调大小/图注、保存重开、导入恢复保持该次 occurrenceId/insertedAt；复制为新的出现位置应有新的插入身份与时间。当前原型稳定 ID 插件仅补 occurrenceId，复制路径的时间语义尚需补验，不能称所有复制/移动路径已完成。
- 回看可按文字锚点理解长文，图片随关联段落显示，也能按实际插入时刻定位；查询必须按来源/出现 ID 去重，不能因两个时间把同图重复投递。具体回看采用哪种呈现策略继续留第三步确定。

例如在旧日记中补上一段写着“2025 年某日 21:00”的文字，今天 21:10 加入图片：正文锚点可表示 2025 年的 21:00，图片 insertedAt 是今天 21:10，保存时间可能又不同。这三个值同时保留，不能互相替换。图像插入时间作为元数据，不自动写一行文字破坏长文排版。

后续只读核对发现现有 2915 篇旧日记均保留原始 createTime/recordTime/updateTime，3 篇当前修改时间不同。源时间没有因导入而全部丢失，用户暂时无需重新安卓导出；统计见 [历史时间审计](validation/2026-10-16-diary-time-audit.md)。本次只建立可行性依据，不代表时间索引已接入或旧数据已迁移。
