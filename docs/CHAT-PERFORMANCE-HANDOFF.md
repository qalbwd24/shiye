- 包装层新消息淡入与上游消息根淡入曾相乘，前几帧过淡。ui15临时接管本次新消息根的透明度/transition，内容从24%可见度起，120ms单层非线性淡入；完成/打断时还原。
- 密集列表取消scroll事件和每动画帧的重复消息扫描，复用上游布局调度器分阶段读写。稀疏列表的300ms占位增长仍有短期逐帧协调。
- 侧栏头像使用192×192中心裁切WebP缩略图，背景保留原Blob；bitmap.close、canvas清零，按assetId复用。替换/删房/退出时回收失效URL，打开的预览保留所需URL，异步代际避免旧结果覆盖。GIF头像变为静态首帧，GIF背景仍用原图。
- 没有调整发送持久化顺序，没有关闭诊断来伪装性能改善。

## 10. 推荐的下一轮顺序与验收

这是开发建议，不代表原因已确认：

1. 建立当前可复现基准：分别测启动恢复、稳定闲置、已确认的正常显示/折叠/最小化、普通发送/表情首次发送/媒体和长草稿。记录硬件、屏幕、实际版本和进程树；明确自动化/截图开销。
2. 对4%左右CPU做原生线程与WebView各角色剖析，确认等待/消息/绘制活动；对私有提交、驻留私有页、JS堆、图像/GPU资源分别取证，测持续使用后的趋势与关闭回收。短期涨落不能直接判泄漏。
3. 在虚构且足够大的库上拆分发送时序，测同步encode/草稿保存、DOM提交、实际可见帧和动画结束；再决定调度/存储/缓存的修订范围。
4. 每次修订查看发送前基准及实际绘制帧。旧节点重建后按消息ID重新查找；要求有效样本，禁止null样本假通过。有效透明度至少算消息根×内容，确认在页脚以上可见；测实际输入事件，不计自动化点击前等待。
5. 保留稀疏/密集历史、新时间标记、左右对齐、窄窗360DIP/200%字号、IME、引用/PNG/MP4/Win+V、连续发送、滚轮/导航打断及减少动画回归。长文原生smooth可能约0.8秒，不把同向未结束动画误当回弹，也不因放宽结束时间漏掉前段闪动。
6. 有意义的修订完成后运行 `npm run check`，在隔离库操作并查看实际画面；写验收记录，再标准保存/备份/升级/启动，核对运行修订、安装哈希、API版本和两屏记忆。
7. 记录用户复验，继续保留仍有长帧、长期内存、物理高刷、真实多屏及未解决CPU项，直到有相应证据再勾选。
