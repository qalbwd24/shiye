## 用户当前意图

- 希望启用新数据结构后，原快捷/主窗输入与阅读体验基本保持。
- 便签按事情/任务长期编辑，多标签、图文及任务层级；本轮询问该如何处理数据，并希望以后与电脑桌面插件联动显示。
- 最终形成“软件书写 → 共同内容与业务数据 → 桌面投射/AI及程序处理 → 同一份数据更新”的闭环。自动投射为用户明确目标；识别规则、AI具体权限和处理方式尚未细化。
- 之前确认的消息主体/时间/回复/评论规则继续用于日记和聊天；便签明确不自动加正文时间戳、不参与朝花夕拾，不因自动保存生成聊天消息。

## 当前实现事实

- 日记/聊天的统一消息后端仍是隔离候选；既有前端通过整篇body/HTML兼容投影接入。启用需要保存/读取适配，不是更换文件后任何前端都无需修改。现有快捷输入已在隔离浏览器验证；旧折叠内容、音频仍有兼容伴随显示。
- 便签UI3使用独立notes.html和静态18770服务。notes-preview-store.js把工作台、正文快照和图片Blob放入 `shiye-notes-ui-preview-v1` IndexedDB；没有便签主库接口、正式备份或跨端同步。
- UI3的Markdown实时预览在活动文字块保留标记，在离开时用编辑器装饰展示；权威文字节点仍有源码。不能假设任意外部richdoc渲染器会自动展示同样效果。
- 现有 `/api/open/v1` 是日记只读DTO及组件客户端，提供日记筛选/媒体/随机与周年读取；当前不提供便签列表、任务勾选或便签变更订阅。不能把既有周年查询称为新朝花夕拾已完成。
- 尚未检查用户现有桌面插件项目。其框架、路径、渲染能力和访问方式在具体对接前另行核对；本轮不猜测它已能接便签。

## 推荐结构（AI建议，待用户确定）

建议在拾页存储服务中区分独立的便签文档、任务、日程对象，复用共同图文格式、稳定身份、媒体库、版本/备份和业务接口。逻辑独立不等于必须拆成几个互不兼容的数据库或另造图片格式；实际文件/表位置后定。便签可整份body为权威文档，不要求额外切成messageStore消息，也不保存另一份可独立编辑的消息正文。

| 来源     | 内容组织                                           | 修改与时间                                                                    | 回看建议                 |
| -------- | -------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------ |
| 长文日记 | 布局组合带时间的内容单元                           | 整篇编辑，手打完整时间锚点、媒体插入时间与编辑兜底并存                        | 使用已确认规则           |
| 聊天记录 | 每次发送是一条内容单元，会话空闲后归篇             | 发送时刻稳定；撤回后新号重发                                                  | 使用已确认规则           |
| 便签     | 独立长期图文文档，保留真实任务层级，不按五小时结篇 | 持续修改同一文档、保存版本历史；内部创建/修改元数据不插正文、不作消息时间锚点 | 用户已明确不参与朝花夕拾 |

正式协议应分开：

1. **正文与媒体**：共同richdoc（保留任务列表真实层级、原始Markdown标记、blockId和媒体出现ID/insertedAt），正文只存在一套可编辑权威来源。便签直接保留文档树，不强制使用日记的时间切分/layout结构；UI3装饰不作为持久节点写入。
2. **归属与属性**：稳定便签ID、标题、分类/标签、归档状态、版本等。便签采用独立文档对象即可，不因“统一”而强制扩展unit.origin.kind或假扮diary。正式对象/接口仍需设计，当前尚未提供便签主库保存路由。
3. **任务/日程属性**：任务有稳定身份，保存层级及完成状态；有需要时再加到期/提醒/重复/时区等明确属性，关联至对应便签/任务。倒计时根据到期时刻实时算，不每秒改正文。任务具体字段尚未定，不抢写schema。
4. **工作台外观**：打开哪些标签、标签顺序、光标/滚动、窗口、背景/透明度、桌面插件位置等，属于本机工作台状态。它们不生成日记消息，也不推进正文事件时钟。

共同正文格式不改变便签持续编辑的语义。勾选待办更新同一任务，历史版本负责保留变更；便签自动保存、归档与修改均不自动进入日记/朝花夕拾。媒体insertedAt等内部元数据可继续保留，用于来源与版本管理，不显示成正文时间戳。

## Markdown与跨视图显示

正式接口需要声明便签正文的源码/渲染语义与版本，或由共享读取服务给出可清洗HTML投影。现有UI3的源文字及标记继续保留，不反复整篇Markdown与HTML往返。桌面显示组件复用同一读取渲染规则，才能兼顾源码输入习惯与非编辑状态格式；不能仅把便签body传给原richdoc渲染器就宣称Markdown预览一致。

## 最终能力需要的数据职责（AI建议，非已实现）

- **共同图文能力**保留文字、图片、视频、Markdown源码、稳定编号与版本；日记/聊天使用消息单元，便签使用独立文档，复用正文格式与资源管理。
- **便签文档**组织长期内容与真实任务层级，保存名称/分类/标签等归属；工作台标签只是打开这些文档的方式。
- **任务与日程对象**绑定内容单元或任务块的稳定身份，提供完成状态、开始/截止/提醒时间、重复/时区等机器可处理属性。这样桌面能列未完成项、日历能按日期展示、倒计时能计算、程序能安排提醒，AI也能检索及修改明确对象。
- 每个字段的权威位置须唯一。正文复选框与任务状态若有两种表现，应由一个业务事务处理命令并同步投影；不把两份可独立编辑的状态留给软件与插件互相覆盖。具体schema/字段位置仍待设计，不抢改当前richdoc校验器或原型存储。
- **桌面投射**是针对相同对象的实时视图；绑定对象ID或筛选规则，持续反映保存后的修改，正文与资源不另复制为一套正式桌面库。
- **AI/程序**通过业务接口读取/检索/创建/修改对象，结果走同样版本与历史规则回写；MCP可作为接口适配层，具体形式待实现讨论。自然语言识别可生成任务/日程属性，但自动识别策略尚未确定，不把每次文字编辑隐式当作新消息或新提醒。
- 便签不进入朝花夕拾，桌面展示/AI处理也不改变这一规则；待办、日程是否另有统计需求后定，不能顺带把它们作为日记回忆来源。

例如“周五交报告”可在便签中书写并关联一项任务；明确截止时间后，桌面待办/倒计时读取同一对象。AI或程序修改该任务的时间/状态后，软件与桌面同时更新；提醒可关联任务投递至聊天。此为解释数据闭环的示例，不代表已确认全部自动识别或推送规则。

## 桌面插件联动建议

桌面插件通过本机拾页业务接口按稳定ID读取便签/任务与媒体，布局自行控制；标题或分类改名不会断开绑定。窗口关闭后仍由拾页后台提供数据，便签编辑窗口无需一直开着。这是接入目标，当前便签静态服务尚不具备。

- 只读显示可复用已有开放DTO客户端的版本化设计，新增便签/任务读取能力；具体端点名称未定。
- 若支持勾选/修改，用专用业务命令携带任务ID及expectedRevision，在同一存储事务内提交；随后便签、桌面插件刷新同一结果，冲突时保留输入。外部程序不直接改diary.json或IndexedDB。
- 自动投射应有变更通知或可恢复刷新机制，多个视图看到同一版本；具体技术方案后定。现有开放接口不含便签事件流，不能据此宣称已经自动联动。
- 本地锁/同源规则沿用现有机制。插件若是另一端口的网页，具体桥接需按其现有宿主适配，不因方案而直接开放任意跨域。
- 以后提醒/倒计时若通过聊天推送，推送记录关联原便签/任务与触发事件，使用稳定投递编号防重复；完成状态仍在原任务。是否保存为回忆来源另定。

## 进入正式主库前的迁移建议

先保留原型profile/IndexedDB，并导出包含图片Blob的可恢复快照；在隔离库导入副本、建立原ID到主库媒体/内容身份的映射，验证Markdown原文字节、编号/待办父子层级、图片原件/出现身份、关闭重开及并发修改。正式启用前保留原型快照，不能只改API地址后把“空列表”当作原内容已迁完。
