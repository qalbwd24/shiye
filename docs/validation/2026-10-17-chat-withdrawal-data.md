# 聊天撤回的数据衔接隔离验收

本轮仅修改数据适配层和隔离测试。按用户最新要求，不操作桌面，不编译宿主，不更新正式进程或真实聊天库。

## 已实现的衔接

- 本地 `DeleteMessages`／`channels.DeleteMessages` 将消息从活动列表移除，并在同一次 IndexedDB 写入中保存无正文的 `shiyeWithdrawnMessages` 和 `shiyeWithdrawalOutbox`。撤回记录保留操作 ID、会话／消息 ID、原发送时间和请求时间。
- 清除自动引用预览，保留用户自己撰写的回复内容。引用对象的稳定 ID 不改变。
- 持久化递增消息编号，并检查撤回记录中的最大编号；撤回最新消息后重发不会复用旧 ID。
- 日记桥优先发送撤回 outbox，不受普通消息的内存确认缓存影响。后端确认后，再等待本地 worker 完成持久化确认，最后清除 outbox。任何一段确认丢失均以相同操作 ID 重试。
- 已停用后续归篇的关联会话仍会投递既有待发撤回；不因此继续投递普通新消息。
- 分类名称失效时，仅在后端存在同一来源／会话的有效新分类时修复本地关联；有效的手动分类选择保持原样。
- C# 桥仅增加固定的 `withdraw → POST /api/chat-journal/withdraw` 允许项，没有任意地址或命令执行能力。

后端负责重复操作幂等、未归档撤回登记、旧 create 请求不可复生及统一内容单元的清除；后端验收由统一数据层报告覆盖。

## 验证

`tests/chat-withdrawal-local.test.mjs` 8 项通过。测试实际执行本地 TypeScript worker 的消息修改、IndexedDB 写入和 JavaScript 日记桥，仅将 Telegram 构造器与宿主 HTTP 桥替换为隔离适配：

1. 撤回后原文不再存在于活动消息和操作记录，自动引用预览清除，重开仍有效，编号不复用。
2. 分类改名后的关联修复及有效手动选择保护。
3. 正常后端确认与本地确认。
4. 后端已提交但回执丢失后的同操作重试。
5. 后端成功、本地确认未送达后的同操作重试。
6. 停归篇后撤回仍投递，普通消息不继续投递。
7. 重复撤回只保留一个操作，按会话撤回不影响其他会话。
8. 固定宿主允许项和两个 JavaScript 镜像一致。

定向 ESLint／Prettier、项目模块引用扫描通过；Telegram Web A `tsc --noEmit --pretty false` 通过。测试正文全部为合成数据。

## 仍未验证／不属于本轮

未构建或启动新宿主，未执行真实 WebView、操作系统输入法、聊天菜单或正式数据库的人工验收。撤回提示气泡、限时“重新编辑”交互及旧资源的物理垃圾回收不由本轮数据桥测试证明；本轮不会删除可能被其他记录引用的媒体文件。当前运行程序不会因为源码和类型检查通过而自动获得这项改动。

源码位于 `previews/telegram-chat/`，测试中间数据使用内存 IndexedDB。公开证据目录为 `outputs/message-unification/`；未生成私人日记样本或桌面截图。
