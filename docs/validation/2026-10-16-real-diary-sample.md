# 真实日记随机抽样：只读处理试验

2026-10-16。用户要求先随机抽一些日记试处理，检查问题。本轮只 GET 正式本机库，在内存进行候选格式解析、内容处理和 JSON 往返；未调用保存/迁移接口，未读取原媒体字节或重启窗口。没有把正文、标题、附件名称或转换后的正文写入报告。

## 抽样与方法

从当时可见、非删除/隐藏/草稿/演示、非聊天归篇的 2997 篇中，按随机种子为 ID 生成排序，抽取 30 篇；另补 Markdown、附件、较长和带完整时间标记的覆盖样本，去重后共 35 篇。候选池含 HTML 2894、Markdown 103、带附件 986 篇；没有正文 HTML 含 img 的篇目，因此此次**没有覆盖真正文中图片转换**。

样本包含 HTML 32 篇、Markdown 3 篇；6 篇有附件，14 篇含可严格识别的完整时间行。补样与随机样本可重叠，不把 35 篇都称作均匀随机。

使用现有 richExtensions/Editor/MarkdownManager 实际解析路径，再经 fromEditorJSON → prepareContent v2 → JSON 序列化/读取 → 编辑器 schema 校验与字段往返。这里只测试当前原生解析能力，**不是已经开发完成的旧格式迁移器**。HTML 图片解析原本即禁用，无法把它的安全限制误报为本轮支持完整迁移。

随机种子、来源摘要及逐样本匿名结果见 `outputs/diary-sample-processing/report.json`；脚本 `tmp/diary-sample-processing/run.mjs`。结果没有逐篇原 ID/标题，仅匿名编号与种子散列身份；同种子在库内容/候选集合变化后不保证完全相同样本。

## 发现的问题

1. **3 篇 Markdown 换行结构与旧 HTML 不同。** 非空白字符没有发现丢失，但空白/硬换行计数不同；当前 Markdown 配置 breaks=false，单个换行与旧渲染的 br 语义不同。未实际渲染对比，不断言每一处都已肉眼合并。
2. **这些 Markdown 的时间识别不足。** 时间标记与其他文字可处于同一段的软/硬换行中；处理器目前只识别独立顶层时间段落，报告 embedded-marker-not-segmented。整个样本中严格完整时间标记共 109 个，处理后识别 98 个，差 11 个，均在上述 3 篇中。
3. **6 篇附件不能自动获得文中位置。** 原附件关联仍在 Entry，且本轮未修改；但附件没有变成正文 image 节点，也没进入当前仅扫描 body 的媒体索引。如果以后只用该正文索引当完整资源清单，会漏附件，必须在 Record/旧格式适配时合并独立附件引用。
4. **4 篇有仅时分/不完整日期等待分类格式。** 处理器正确提示 unclassified-time，但仍可能让部分内容时间未知；不能宣称全部历史写法已识别，后续需补明确规则并保留来源。

附件、换行、时间警告可在同一篇共存；上述数量不能相加当作失败篇数。附件不一定全为图片，本轮未读文件字节，不把附件数量称作图片数量。

## 下一轮应先修什么

- 在旧 Markdown 读取适配里保持原换行语义，以原文/原渲染为依据，不能靠删换行消除检测差异。
- 在不拆改正文排版的前提下，让时间索引识别段落内部的时间行；定位必须带来源版本，临时文字偏移不能当作永久评论身份。
- 把旧附件与文中图像引用同时纳入完整媒体清单；没有原始位置时保留原附件区，insertedAt 仍未知，不能自动塞到某段或补当前时间。
- 对以上问题使用虚构结构补回归，再用同批实际日记重复只读比较。通过后再考虑更大抽样，尚不启动全库转换。

本轮只更新需求/设计/验收与临时只读工具，没有修改运行处理器、旧数据或 UI。未因抽样再次重复应用全库测试；上一轮 353 项检查属于此前源码快照，不能代替此次真实样本的差异结论。
