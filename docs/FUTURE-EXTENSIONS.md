已确认的便签定位继续保持：

- 接近Notepads：打开就写、按事情命名、多标签、自动保存、下次继续。

- 原型内容、图片和profile保留；当前仍是独立试用存储，不能把UI可用当作正式主库/同步已经接通。
- 现有复选框、清单、编号、子步骤属于便签编辑功能；其继续完善不等于现在启动一套独立任务/日程后台。
- 保存/恢复可靠性与已确认的基础使用问题照常处理，不通过新建生活管理体系来改变便签使用方式。

具体存储字段、是否复用某个主库对象、正式迁移和新同步方案仍未定。本文件不触发迁移，不清空或覆盖任何试用内容。

## 暂存的扩展方向

下列是用户表达过的最终设想，待实际使用反馈后再细化。它们不按“第一版/第二版”预先收窄，也不要求现在一次实现全部能力。

| 方向         | 用户设想                                          | 需要以后结合使用再决定                                             |
| ------------ | ------------------------------------------------- | ------------------------------------------------------------------ |
| 待办         | 在软件中书写并管理要完成的事情，可有子步骤        | 自由清单是否足够，何时需要独立任务、截止/提醒等属性                |
| 日程         | 管理某个日期/时间段的安排                         | 创建方式、日历呈现、提醒与重复规则                                 |
| 习惯打卡     | 记录持续做某件事的完成情况                        | 一次/多次、计数/时长、补记/撤销以及统计方式                        |
| 桌面自动投射 | 软件中的便签、待办、日程等自动显示到桌面插件      | 显示哪些内容、如何绑定、是否需要桌面交互与更新机制                 |
| AI或程序处理 | 读取、提取、整理或修改相关内容/事项，并反馈到软件 | 明确哪些操作有实际用途、自动识别策略与接口形式                     |
| 多端互通     | 手机、电脑、手表及可能的互联设备/中枢协作         | 实际设备平台、离线场景、传输与冲突规则、自有服务器或设备转发等路线 |

提醒、倒计时等以后可关联原任务/日程，在随想中投递信息；这只是已讨论的扩展方向，尚未接入真实服务，也不自动纳入日记回忆。

## 暂时保留的数据设计原则

这些是避免将来难以衔接的设计备忘，不是已确认schema：

1. 日记与随想继续已有的消息主体方向；便签、任务、日程、习惯/打卡可以采用各自合适的业务结构，不强制变成日记消息。
2. 图文内容、资源身份、版本、备份和本机读写服务可以复用；具体是同库分表、分文件或其他方案以后再选。
3. 便签是持续修改的文档。习惯规则与每次打卡记录分开，任务/日程有自己的业务状态和时间；内部创建/修改元数据不等于正文显示时间戳。
4. 未来桌面/手机/手表展示或操作同一个稳定对象，避免各自维护会相互漂移的正式副本。离线缓存、操作重试与冲突处理需要明确设计。
5. AI/程序使用业务接口处理数据，具体接口或MCP路线未选；不因此自动开放文件写入或直接改正在运行的数据库。
6. 便签不参与朝花夕拾。其他生活事务数据是否需要统计/引用另议，不从“可共享接口”推导为必须兼容日记回忆。

现有日记WebDAV兼容协议不代表已经实现通用生活数据与手表同步。

## 使用后值得回头讨论的问题

用户无需现在逐条回答，也不预设必须记录一份反馈表：

- 实际常开的便签是什么，哪些需要持续修改，哪些很快就不再查看？
- 现有清单/编号/折叠是否已经足够？哪种遗忘或重复操作值得增加任务、提醒或日程能力？
- 哪些信息确实希望在桌面常驻，哪些只在软件里打开即可？
- 手机/手表最需要完成的动作是什么，是否经常离线？
- AI或程序在哪个具体步骤能减少操作，而不是增加配置负担？

等使用习惯逐渐清楚，再根据具体场景讨论数据契约、交互和实施范围。本文件不创建排期、后台提醒或自动回访。
