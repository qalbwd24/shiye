# 日记、消息与媒体的统一数据方案调研

日期：2026-10-16。状态：需求整理与候选方案，未选定最终 schema，未实施迁移。

本轮只处理数据、导出和未来回顾服务的设计。另一对话正在改 UI，本轮不修改界面、运行程序、真实日记或消息库。项目代码依据为 `D:/拾页` 当前工作副本；旧正式数据仍在原 F 盘项目。

## 最新：只读归篇与具体数据契约

用户已确认聊天归篇正文只读，修改从聊天端撤回/重新编辑，日记侧只看与评论；评论不进入回看。朝花夕拾无引用默认评论最近展示组，有引用只回复单条，输入框显示目标并可切换。具体字段、样本、关系校验和当前代码适配见 [统一数据契约 v1 草案](UNIFIED-DATA-CONTRACT-V1.md)。本轮没有运行库变更；下文旧阶段候选以最新确认优先。

## 最新澄清：分类统一与“朝花夕拾”

用户本轮进一步明确：聊天也有分类，可复用已有分类或自行设立；两种入口尽量共用图文结构，聊天另保留会话归属。回顾改为“现在回去看到过去，并留下今天的评论”：按间隔同时显示多个历史周期，避免每次重复复制正文。间隔改变不能让旧评论失去上下文；当前倾向评论不自动再次参与回看。头像/用户名未定，微信接入暂缓，移动端倾向自有安卓客户端。

具体需求与技术可行性必须平衡。新图文结构仍需桌面、安卓、中文输入及导出适配验证，不把统一 schema 等同于立即替换编辑器或数据库。最新方案及待定项见 [朝花夕拾设计](MEMORY-REVISIT-DESIGN.md)，优先于下文旧阶段的投递叙述；本轮仍只更新文档。

## 1. 本轮用户需求

### 已明确

1. 长篇日记与聊天式随记需要相互衔接，并比较统一格式和分别存储的代价。
2. 长篇正文中的可见时间戳继续由用户自行输入，不能强制改成自动时间段。
3. 消息保留自身发送时间、身份、图片、引用、附件等信息，不能归篇后只剩拼接文本。
4. 不满足于只能在正文之外看附件；希望图片能位于文字之间，并支持一定排版，体验参考 Word。
5. 讨论按时间截断、自动进入日记正文的规则，以及分篇是否可用属性/标记表达。
6. 希望“朝花夕拾”同时展示多个历史周期相应时刻的内容，现在回看并留下今天的评论；自建云可辅助同步/查询，不以每次复制旧消息为目标。
7. 本轮先整理需求、广泛调研实现路径，不立刻改格式或迁移旧数据。

### 继续有效的此前约束

- 每个话题默认连续 5 小时没有新增消息才分成另一篇，时长可配置；不按零点硬切。30 分钟只用于聊天中显示时间分隔，两者独立。
- 消息发送后可靠保存，不等满五小时才第一次落盘。
- 撤回后长期只保留撤回提示；原文只短暂用于重新编辑，不进入长期搜索、引用预览、导出或往日回顾。
- 历史身份与当前资料的关系需要保留扩展能力；用户最新表示头像/用户名方案未想好，不锁定每条消息必须采用哪种展示。
- 主窗、快捷写作与消息窗口共享业务数据；Telegram 客户端代码只作为前端基础，不使用 Telegram 服务或协议对象充当拾页长期数据格式。
- 手机互通方向保留。现有一本日记 Android 兼容接口与未来自有手机客户端是两条不同适配路径。
- 正文非线性分块/分栏、树状思考 UI 继续暂缓。内部用文档节点表达段落，不等于重开该 UI 需求。
- 日记内 AI 侧栏与随记话题是不同业务；单篇唯一 AI 对话流作为该篇的一部分保存，具体逻辑后议。

### 尚未决定

- 富文本文档的最终 schema、是否及何时替换编辑器、是否迁移 SQLite。
- Word 式排版做到图片尺寸/对齐/表格，还是进一步做到分页、浮动环绕、打印版式。
- 聊天归篇只读已确认；具体分类/标题管理权限与撤回后重新发送的时间和 ID 规则仍待细化。
- 回顾按日历月/年还是固定时长，旧内容编辑后回顾哪个版本，离线补送与通知策略。
- 自建服务器、加密、手机同步和 AI 访问权限的具体选择。本轮不据此取消原有加密设计。

## 3. 四条数据路线比较

以下取舍为 AI 建议，不是已经确认的实现要求。

| 路线                                                  | 长处                                                       | 对当前目标的主要代价                                                                   | 判断                                          |
| ----------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------- |
| A. 正文用 Markdown，消息保留元数据，图片单独引用      | 文本易读、AI 输出接入方便、迁移较小                        | 图片宽度、图注布局、复杂表格等需要扩展语法；从富文本来回转会丢属性                     | 若只想基础图文，这是可行低成本路线            |
| B. 正文用 HTML，消息另外保存                          | 接近现有日记，可直接显示图文                               | 显示结构与业务语义混在一起，引用和时间难稳定定位；清洗规则可能丢版式；不同端生成差异大 | 适合旧内容兼容/阅读投影，不推荐作为新统一契约 |
| C. 日记与消息共用结构化富文档内容，外层保留各自元数据 | 图文顺序、格式、引用和 AI 内容可复用；能形成多种视图和导出 | 需要版本化 schema、Markdown/旧 HTML 适配器及编辑器验证                                 | **最符合这次长期方向，建议优先验证**          |
| D. 所有东西都塞成一个连续正文或直接保留 Telegram 对象 | 第一版看起来少设计                                         | 消息身份/撤回/回复/回顾语义容易丢失，长期绑前端内部结构；任意一处编辑影响全篇          | 不建议作为长期基础                            |

Joplin 是路线 A 的实际参照：富文本编辑仍落为 Markdown，因此官方明确列出格式转换和插件兼容限制。这说明基础图文可以用 Markdown，但不能承诺任意 Word 排版都能无损往返。[Joplin 富文本说明](https://joplinapp.org/help/apps/rich_text_editor/)

## 4. 推荐模型：共用内容结构，保留文档与消息的区别

### 4.1 共同内容层

使用带版本的文档结构，基本构件包括段落、文本格式、标题、列表、代码块、分割线、图片、视频、文件卡片、引用；表格和时间标记按范围逐步加入。底层节点可以嵌套，但界面仍是用户熟悉的连续图文页面。

示意结构，仅用于讨论，命名与字段都未定稿：

```json
{
  "schema": "shiye.document",
  "version": 1,
  "type": "doc",
  "content": [
    {
      "id": "block-demo-1",
      "type": "paragraph",
      "content": [{ "type": "text", "text": "一段虚构的记录" }]
    },
    {
      "id": "block-demo-2",
      "type": "image",
      "attrs": {
        "assetId": "asset-demo-1",
        "alt": "示例图片",
        "widthRatio": 0.6,
        "align": "center",
        "caption": "虚构图注"
      }
    },
    {
      "id": "block-demo-3",
      "type": "paragraph",
      "content": [{ "type": "text", "text": "图片后继续写。", "marks": [{ "type": "italic" }] }]
    }
  ]
}
```

这是应用自己维护的 schema，可采用 ProseMirror 兼容的节点/标记规则，并固定扩展契约；不直接把任意版本编辑器吐出的所有字段当成永久标准。Tiptap 官方建议将结构化 JSON 用于持久化，它和数据库类型独立。[Tiptap 持久化](https://tiptap.dev/docs/editor/core-concepts/persistence)

稳定 ID 优先加在需要引用的内容块上，文本细节不必每个字都分配业务 ID。对于块被合并、删除和拆分，要规定引用失效或映射规则。块 ID 有助于定位，但本身不等于自动解决并发冲突。

### 4.2 外层业务对象

| 对象                | 自己负责的信息                                               | 共用的信息                             |
| ------------------- | ------------------------------------------------------------ | -------------------------------------- |
| 长篇文档            | 篇目 ID、标题、分类、用户选定日期、版本                      | `body` 富文档、媒体引用                |
| 消息                | 消息 ID、话题 ID、发送时间、发送者快照、回复目标、状态、修订 | `body` 富文档、媒体引用                |
| 聊天归篇            | 归篇 ID、成员消息、标题/分类、空闲间隔、状态、归篇规则版本   | 从消息读取内容，不再成为另一份独立原文 |
| 回顾投递            | 来源 ID、规则 ID、计划时间、实际投递时间、投递状态           | 显示源内容，或按明确规则生成快照       |
| 待办/提醒等未来对象 | 截止时间、完成状态、重复规则等领域字段                       | 共用内容和媒体；通知可呈现为消息卡片   |

统一格式不要求把长篇的每个段落伪装成聊天消息，也不要求待办的完成状态藏在一段文本里。共同内容模型解决“写了什么”；外层对象解决“谁在何时发了什么、它有什么行为”。

### 4.3 原文、解析结果与阅读缓存

- 新富文档以结构化内容为权威版本，HTML、纯文本、搜索索引是可重建的投影，带来源 revision/渲染版本。
- AI 返回的 Markdown 或用户输入的 Markdown 可以保留准确原始输入，同时按统一语法解析。原始输入是来源材料；不能让它和富文档长期同时作为两个可随意改写的权威正文。
- Markdown 源码模式只对能往返的子集承诺编辑；遇到图片版式或自定义节点，不静默降级后覆盖。可保留原节点或显式“转换为简化 Markdown”。
- 不认识的旧字段或未来节点需要保留并提供降级显示；不因当前端不会画就删除。

“完整 Markdown”需要一份明确语法约定：建议 CommonMark + GFM，并显式列出高亮、数学、脚注、图表等扩展的支持范围。`==高亮==` 是扩展；`__文本__` 在 CommonMark 是加粗，斜体是 `*文本*` 或 `_文本_`；围栏代码用三个反引号。既有 Telegram 输入快捷语法与日记解析器不能各自解释同一源码。[CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/)、[GFM 规范](https://github.github.com/gfm/)

### 4.4 媒体资源与图片位置

资源只存文件本身和元数据：`assetId`、MIME、大小、哈希、原文件名、原件/派生版本、拍摄时间来源等。文档节点决定在哪里显示、宽度、对齐、图注和本次裁剪。

因此同一张图在消息里是缩略图、在长篇里居中宽图、在回顾里再次出现，都可引用同一资源。改变某处显示宽度不改原件；缩略图不能代替唯一原件；已不可逆压缩的旧图无法凭新 schema 恢复清晰度。原件保留的默认策略另行确定。

内部引用使用 `assetId`，本机 `/media/id` URL 只是显示时生成的地址。导出时映射相对路径或内嵌资源，不能把本机 URL 当作可携带文件。资源删除按全部引用计数/可达性决定，不能撤回一条消息就删掉其他篇也在使用的图。

Tiptap 图片扩展支持块内/行内展示和当前文档所述的调尺寸机制，但上传保存需另外接业务层；要在项目实际安装版本上验证可用范围，不能把最新文档功能视为当前已接好。[Tiptap Image](https://tiptap.dev/docs/editor/extensions/nodes/image)

### 4.5 时间的不同含义

- 消息 `sentAt`、服务器收到时间、内容编辑时间、回顾计划时间、实际投递时间分开。
- 日记的用户选定日期，不自动等于每段内容实际发生时间。手打的时间戳保持原文，不用正则猜测并拆分所有旧日记；没有准确段落时间就诚实保留“未知”。
- 自动时间保存绝对时刻，显示默认 `Asia/Shanghai`，允许跟随系统；需要日历语义的规则另外保存 IANA 时区。VPN 的 IP 位置不作为时间依据。
- 导入无时区的历史日期保留原字符串、精度和来源，不擅自当作 UTC；排序同刻消息使用稳定次序字段/ID，不能只靠格式化后的分钟。
- “一年后同一天同一时刻”与“365×24 小时后”不同；三个月也不能固定等于 90 天。闰日、月底、夏令时和无效本地时刻需要策略。

时间表示可参考 [RFC 3339](https://www.rfc-editor.org/info/rfc3339/) 和 [IANA 时区库](https://www.iana.org/time-zones)；日历加法与实际时长差异见 [Temporal 时区日期加法](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Temporal/ZonedDateTime/add)。是否引入相应运行库需实施时验证。

## 5. 五小时分篇的意义：组织关系，与文件分割分开

举例：20:00、22:00、次日 02:00 各发一条，消息间隔均小于五小时，属于同一篇。下一条 08:00 距离前一条六小时，进入下一篇。零点不造成分篇。

建议让数据库保存消息本体，分篇保存消息成员关系及规则：

```text
话题 A
  消息 m1、m2、m3 → 归篇 s1 → 日记列表里的一篇
  消息 m4、m5     → 归篇 s2 → 日记列表里的另一篇

聊天视图：连续读取 m1…m5
日记视图：按 s1/s2 汇集相同消息
往日回顾：按 m2 的原始发送时间定位，不依赖 s1 的标题
```

分篇提供标题、分类、统计、检索和导出的管理单位，所以仍有意义。文件到底是一个 JSON、多个 JSON 或一个数据库，并不改变这个用途。若未来想改为连续查看，可以换视图，不必重新拆并原文。

建议细则，仍待讨论：

- 每条消息发送即保存；归篇从第一条存在，五小时后只是关闭这组的追加窗口。
- `gap >= idleHours` 的边界需固定并测试。已形成的组保留规则快照，调整设置默认只作用后续，历史重分另设显式操作。
- 消息编辑、撤回不是新增消息；回顾机器人投递是否延长原话题的五小时窗口需单独决定，建议不默认干扰个人随记归篇。
- 离线消息补传依据原始时间、稳定次序和去重 ID；晚到消息不能简单重排整库、改变已被引用的篇目 ID。需设计可解释的补入或新组规则。
- 当前桥接代码对过早时间和冲突会拒绝；它还不是具备上述离线重整能力的最终模型。
- 不用一套“时间截断”兼任所有用途：30 分钟是显示分隔；5 小时是日记归篇；AI 上下文按内容/额度切块；回顾按来源时间调度；分页/懒加载按性能需要。

## 6. 最新确认：聊天归篇只读，源消息与评论分开

用户现已确认：聊天消息整理形成的日记正文只读，不在正文端修改；改动从原聊天端撤回、重新编辑处理。日记侧可浏览与评论。既有自由书写的长篇仍保持原文编辑能力。

自动归篇按同一批消息形成日记阅读视图，原消息、时间、图片和引用保留。评论是独立记录及关联，不修改原消息，也不反过来作为回看来源。此前额外“整理成可改写文章”的 AI 建议不作为当前要求。

当前代码仍采用消息嵌套 + HTML 投影，并用人工修改检测避免覆盖；尚未执行后端只读和撤回同步契约。下一步适配需同时处理普通 PUT、快捷保存、历史、搜索/引用缓存和桥接回执，具体见 [统一契约](UNIFIED-DATA-CONTRACT-V1.md)。

## 7. 编辑器与内容格式的实现路径调研

| 路线                       | 官方能力依据                                                   | 适配判断与限制                                                                                                                                                           |
| -------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ProseMirror / Tiptap       | 文档节点、标记、schema；Tiptap 可保存 JSON、显示图片并扩展节点 | **优先做隔离验证**。聊天 vendor 已有 `@tiptap/core` 3.x 依赖，长篇目前仍是 CodeMirror；可复用知识但不是零成本换编辑器。采用项目自己的 schema，不绑 Telegram 内部实体偏移 |
| BlockNote                  | 以稳定 ID 的块组成文档，含富文本和图片等块                     | 内容块寻址很直观，可作 schema 参照；成套 UI 的适配成本、样式、输入法要验证，不因其有块就重新启用分栏设计                                                                 |
| Lexical                    | 编辑器状态、序列化、可扩展节点                                 | 可以实现此类模型，但会新引入另一套节点体系与适配；当前无证据显示比复用已有 Tiptap 更省事                                                                                 |
| Quill Delta                | JSON 操作序列表达文本属性和嵌入对象                            | 适合图文与格式，文档与变化表达清晰；与既有 ProseMirror 系输入、表格/自定义语义需要额外转换                                                                               |
| 保留 CodeMirror + Markdown | 当前长篇入口，源码编辑和 AI 文本方便                           | 可先统一媒体和 Markdown 语法；图片尺寸等需扩展。作为兼容/源码模式仍有价值，不能与完整富文本互转时静默丢属性                                                              |

官方入口：[ProseMirror Guide](https://prosemirror.net/docs/guide/)、[Tiptap 持久化](https://tiptap.dev/docs/editor/core-concepts/persistence)、[BlockNote 文档结构](https://www.blocknotejs.org/docs/foundations/document-structure)、[Lexical 概览](https://lexical.dev/docs/intro)、[Quill Delta](https://quilljs.com/docs/delta)。ProseMirror Guide 初次查询取得资料，后续复取遇到 403；不依赖无法复取的细节证明当前集成已可用。

许可与服务边界：Tiptap 开源仓库核心采用 MIT，商业产品/扩展另查；BlockNote 仓库说明普通源码 MPL-2.0、XL 包另有 GPL-3.0/商业许可。不能把文档中的所有导出/分页功能都视为免费核心。核对依据：[Tiptap 仓库](https://github.com/ueberdosis/tiptap)、[BlockNote LICENSE](https://github.com/TypeCellOS/BlockNote/blob/main/LICENSE.txt)。本轮没有安装或复制新依赖。

**Word 体验的工作量分层：**

1. 文字间插图、图注、固定/相对宽度、对齐、基本列表与表格：成熟编辑器路径，需做本地资源、中文输入和持久化适配。
2. 图片拖放、粘贴、裁剪、移动端手势、撤销与版本兼容：有成熟基础，但仍需完整业务验收。
3. 浮动环绕、页眉页脚、分页精度、跨设备字体一致、DOCX 高保真往返：明显更大项目，不建议默认纳入第一轮。

不承诺更换正文 JSON 就能消除现有 UI/IME/图片缩放 bug；那些仍需在相应入口修复。

## 8. 物理存储：建议逐步考虑 SQLite，正文仍可保存 JSON

| 方案                                   | 合适用途                              | 主要代价                                                             |
| -------------------------------------- | ------------------------------------- | -------------------------------------------------------------------- |
| 继续整库 JSON + media                  | 保持兼容，先验证业务契约              | 高频消息每次整体克隆/写文件；多端冲突与查询需要额外机制              |
| 每篇/每消息 JSON 文件 + 索引           | 易人工浏览、独立复制和故障定位        | 跨文件事务、引用一致性、撤回清理和索引恢复更复杂；不是天然同步系统   |
| SQLite 表 + 每条内容 JSON + media 文件 | 本地桌面长期消息、时间/关系查询、事务 | 需要明确迁移、备份和数据库适配；不应让云盘直接同步正在写的数据库文件 |
| 自建服务器关系数据库 + 资源存储        | 手机互通、调度和多客户端              | 增加鉴权、运维、同步和离线设计；单用户不必一开始就上复杂集群         |

**候选默认：本地 SQLite + 行级消息/文档 + JSON 内容 + 独立媒体。** 先定逻辑契约，再决定迁移窗口；不需要为了今天讨论就把正式库搬走。SQLite 的定位适合设备本地应用数据；它支持 JSON 函数，JSON 内容与关系表并不矛盾。[SQLite 适用场景](https://sqlite.org/whentouse.html)、[SQLite JSON](https://sqlite.org/json1.html)

关键约束：

- ID、话题、发送时间、回复关系、状态和 revision 等查询字段独立建列；富文档作为 JSON 保存。不要把全部消息塞到某一行无限增长的数组里。
- WAL 可改善读写并发，但仍须串行化/事务管理写入；数据库、WAL 和媒体的备份要一致。采用官方备份机制或受控快照，不只复制主数据库文件。[SQLite WAL](https://sqlite.org/wal.html)、[SQLite Backup API](https://sqlite.org/backup.html)
- 正文、消息和附件引用一起事务提交；媒体文件先暂存校验，失败可回收，不能出现“数据库说上传成功，文件却不存在”。
- 中文搜索不能因启用 FTS5 就宣布完成。默认 unicode61 不等于中文分词；trigram 的 MATCH 对少于三个字符有限制。需为一字/两字查询设计包含匹配或分词索引，引用和撤回过滤一致。[SQLite FTS5](https://www3.sqlite.org/fts5.html)
- 桌面与手机同步逻辑对象/变更和资源哈希，不互相覆盖整份 SQLite 文件。先做 revision 冲突与离线重试，再考虑并发同文档协作。
- Yjs 等适合确有跨端同时编辑需求时评估；其同步状态是二进制更新，不能只存一次普通 JSON 就宣称保存了完整协作状态。当前不以引入 CRDT 为前置条件。[Yjs Document Updates](https://docs.yjs.dev/api/document-updates)、[Yjs 离线支持](https://docs.yjs.dev/getting-started/allowing-offline-editing)

## 9. 引用、撤回和版本

引用以稳定 `messageId` 或 `documentId + blockId` 表达；显示摘要来自当前允许展示的来源。可以借鉴 Matrix 以事件 ID 建立回复关系、对被移除内容保留必要关系元数据的思路，不需要引入 Matrix 服务。[Matrix 回复与 redaction](https://spec.matrix.org/v1.19/client-server-api/)

根据用户既有选择：撤回后正文为空/不可展示，保留 ID、发送时间及撤回状态；短暂重编辑内容有到期时间且不进长期归档。检索、HTML 缓存、引用摘要、媒体可达性、AI 上下文、待发送回顾和导出都要共同过滤。

保存“操作发生过”的审计状态，不等于永久保存每次操作的原文。不能采用永不清理的 append-only 内容日志，然后只在界面隐藏撤回消息。旧备份/已导出文件的处理另设保留策略；不能承诺撤回会自动抹掉用户以前导出的独立文件。

正常长篇修订和消息编辑是否保留历史、保留多久，可单独设置；撤回的清理规则优先于普通历史保留。来源快照与回顾机制不能成为绕过撤回的新副本。

## 10. 导出应分成三份契约

### 无损携带与恢复

建议提供版本化的目录或 ZIP：

```text
manifest.json           格式版本、范围、时间、文件哈希、兼容信息
records/documents.jsonl 长篇及其当前富文档
records/messages.jsonl  消息、时间、身份快照、状态、回复关系
records/segments.jsonl  归篇与成员关系、规则快照
records/topics.jsonl    话题、分类和需要携带的配置
records/relations.jsonl 跨记录关系（是否独立文件待定）
assets/...              实际媒体字节及资源元数据
```

这只是打包示例，不是已确定协议。按需可一个 JSON 包含所有记录；JSONL 有利于流式处理。必须带稳定 ID、schema 版本和引用映射，区分全量/范围导出、当前版/含允许历史、配置/凭据、本机偏好/跨端设置。恢复不默认激活原回顾任务或覆盖本机热键。未含凭据的可读包和现有加密备份继续区分。

部分导出遇到引用外部消息时，保留目标 ID 与“未包含来源”说明；是否补带依赖可选，不能悄悄扩大全库导出范围。附带引用摘要也须检查撤回状态。

### 供人阅读

| 目标              | 应保留                                         | 可接受的降级/边界                                                       |
| ----------------- | ---------------------------------------------- | ----------------------------------------------------------------------- |
| Markdown + assets | 内容顺序、常见格式、图片、代码、可读时间与引用 | 图片宽度/对齐等需扩展或导出说明；不能承诺所有版式无损                   |
| 独立 HTML/HTML 包 | 图文、时间、样式、消息引用锚点                 | 媒体内嵌或打包；不依赖本机 URL，也不默认联网取图                        |
| PDF               | 可阅读和打印的固定结果                         | 不是可恢复业务数据库；超宽表格、长代码和中文字体需检查                  |
| DOCX              | Word 可编辑的图文文稿                          | 需要专门转换与中文排版验收；消息 ID、动态回顾规则不靠 Word 正文完整保存 |
| TXT               | 文字、时间、图片/附件占位与说明                | 明确不含富文本排版                                                      |

默认可按现有五小时分组输出每篇，也应支持整话题/时间范围连续导出。分篇规则决定组织方式，不决定保存文件必须拆成多个。日期目录按选定导出时区生成，清单记录该时区。

Pandoc 的读取器—中间文档—写出器路线可作为 Markdown/HTML/DOCX 转换候选，官方明确转换不保证全部样式无损；因此导出适配器应列清支持矩阵，而不是用“支持 DOCX”承诺 Word 高保真往返。[Pandoc 手册](https://pandoc.org/MANUAL.html)

### 供 AI / MCP 读取

按记录或内容块输出 JSON/JSONL：正文纯文本/Markdown、来源 ID、消息或块定位、准确时间及精度、媒体 ID/类型、关系和 revision。图片按明确读取请求提供文件，不把整库二进制 base64 塞入每次上下文。

检索后按需要返回有限上下文；AI 的切块不被五小时归篇强制绑定。修改通过业务 API 带 revision 提交，不能直接让 AI 编辑运行中的数据库文件。工具输出与用户正文分字段，避免将工具/系统提示误认为用户写下的日记。MCP 是访问契约，不能代替底层数据模型。

## 11. “朝花夕拾”：现在回看过去并评论

本轮用户修正了核心语义：以一个可调整时间间隔，同时看到去年、前年等多个历史周期相应日期与时刻的内容；不希望每次重现就复制一份完整正文。长篇的时间戳、图片插入时间也应能提供回看定位。

最新 AI 建议：回看规则用于查询/显示原始记录；评论固定关联当时选中的具体来源 ID，并记录今天的时间。对一组历史内容的评论可以保存一次、关联多处，调整间隔不会重算旧评论目标。现阶段不把这一建议写成已确定的多目标评论实现。

不要求每次刷新生成持久投递消息；评论时可保存当时所选来源集合和规则信息。来源被修改后的版本处理、撤回、长篇时间锚点与分组窗口仍需设计。具体已确认方向、候选模型和分步验证见 [朝花夕拾设计](MEMORY-REVISIT-DESIGN.md)。

此前队列/定时投递的调研仅保留为将来通知能力的备选，不再作为回看本身必须依赖的基础。可靠通知可参考 [事务发件箱模式](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/transactional-out-box-cosmos) 与 [BullMQ 幂等任务](https://docs.bullmq.io/patterns/idempotent-jobs)；本轮不引入它们。

## 12. 兼容与渐进实施建议

1. **先定契约**：列内容节点、媒体引用、时间含义、消息状态、归篇关系、导出范围；保持当前 UI 接口继续可用。
2. **隔离样本验证**：仅用虚构长篇、真实输入路径产生的测试消息和本地测试图，验证 Markdown、图文和关系，避免再次只验收手工合成 entities。
3. **新内容试用**：通过适配层生成旧读取端需要的 HTML，旧日记继续按原格式读；新结构与显示缓存绑定 revision。不是让新旧两个字段各自接受不同编辑。
4. **旧内容按需转换**：保留原 HTML/Markdown、未知字段、原件备份和 ID 映射；不批量从手打时间推断消息。仅附件而无正文位置的旧图不能猜插入位置，可保持附件区或由用户补入正文。
5. **再迁移物理存储**：SQLite 与现有 JSON 格式双向样本校验，切换只设一个权威写入口；保留回退快照，不双写两个可被独立编辑的正式库。
6. **补齐导出/恢复**：先保证可携带包能在全新隔离库恢复全部关系和媒体，再做 DOCX 等阅读格式。
7. **手机与云服务**：自有客户端读相同契约；旧 Android 只走有损适配，保存丰富字段的影子数据或阻止旧端覆盖不认识的内容。同步、调度、通知分开验收。

当前一本日记 Android 旧协议不会因电脑换成 JSON 富文档而自动拥有新版图片排版、引用和回顾。若继续用旧客户端，必须明确降级范围；若开发自己的手机入口，则可以共用新逻辑 schema 和响应式阅读组件。

## 13. 之后实施时的验收清单（本轮未执行）

- [ ] 长篇和消息采用相同节点渲染，普通中文、输入法实输、换行、空格、emoji、表情包正常。
- [ ] Markdown 标题、强调、加粗、代码、列表、表格、高亮和扩展按同一契约处理，不能仅合成测试能显示。
- [ ] 图片插于两个段落之间，保存/重启/导出/恢复后位置、图注与尺寸一致；原件哈希不因调宽改变。
- [ ] 同一图片跨消息和日记复用，撤回其中一条不破坏其他引用。
- [ ] 跨零点、恰好五小时、连续零散发言、改间隔、离线补传的归篇行为明确且稳定。
- [ ] 同一消息在聊天、日记关联视图、搜索、回顾和导出中状态一致。
- [ ] 撤回原文到期清理；引用摘要、历史索引和导出不会重新暴露。
- [ ] 手打时间戳原样保留，旧正文不被自动拆分或改时区。
- [ ] 引用跨篇/跨话题、源被删、范围导出漏源、恢复重映射均可解释。
- [ ] 物理迁移可回退，记录/媒体哈希/关系数/未知字段保留；中断不丢已确认保存消息。
- [ ] 新手机与电脑离线冲突能保留双方工作；旧 Android 降级不覆盖 richer 数据。
- [ ] 回顾按日历年/月的月底、闰日、系统时区变化、服务器重启、离线补送和重复重试验证。
- [ ] 可携带包在另一隔离目录恢复，图片不依赖原电脑 URL；阅读格式的排版损失有说明。

## 14. 讨论时最值得先确定的三点

1. 图文目标先做到“连续文档中的图片、调宽、对齐、图注和基本表格”，还是确实需要 Word 分页/环绕？建议先前者。
2. 聊天归篇只读已确认；实施前细化后端只读范围、分类/标题管理权限及源消息撤回同步。
3. 回顾最先按自然年/月重现同一墙钟时间，还是按固定天数？建议把两种规则分开保存，具体默认再选。
