## 1. 前端不被数据格式绑架

| 用户入口                    | 必须保持的行为                                                                          | 数据适配方式                                                                       |
| --------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |

| 快捷窗查看/编辑旧篇         | 能继续打开和使用，原图片/附件/文字不因缺新字段消失                                      | 按原格式分派旧 HTML/Markdown 读写；不能为接新框架强制全库转换或把所有旧篇改成只读  |
| 聊天普通消息                | 正常发送、回复、图片/表情包/附件显示、历史和去重                                        | 统一消息正文及附件映射；会话/作者/发送时刻/引用身份由消息关系层维护                |

| 原日记/消息的评论           | 按篇查看，标明具体消息/图片目标                                                         | 使用稳定来源关系，不依赖分类名称或正文文本偏移                                     |

## 2. 分类、标签等是可变属性

正文、资源位置与属性是不同修改范围，但均通过版本检查和统一存储提交：

- 分类和标签随前端新增/修改/删除/排序，读取时取最新记录和实时分类表；处理器不能缓存初始化时的 library，也不能用旧处理结果覆盖最新属性。
- 稳定 recordId/pageId/blockId/occurrenceId 不随分类改名、标签修改或排序变化；消息引用和评论目标仍指原内容。
- 未来稳定分类 ID 与展示名称分开；旧名称映射通过读取适配逐步接入，不能一启动就给全部旧日记补字段。
- 会话默认分类影响后续消息；篇目现有分类可以由用户管理。分类整体“改名/合并”不是改变消息会话，也不能伪装成用户修改了正文。分类移动与会话默认值改变的分篇策略需单独适配，不拿正文只读禁止分类/标签管理。
- 旧字段、原格式、评论及附件关联必须在保存时保留，禁止用处理器返回值替换完整 Entry。现有 PUT 是完整对象＋revision，不支持只发 `{category,tags}` 当作 PATCH。
- 共享文档是单一正文，聊天归篇正文只读；类别/标签可改不意味着允许在日记端改写原聊天消息。正文读写权由服务端验证。

## 3. 正文编辑时间与属性更新时间分开

只改标签、分类或置顶，会改变记录版本/updatedAt，但不应把原文的无时间戳部分变成“刚写的内容”。新正文保存层需要显式维护内容时间上下文（候选 contentEditedAt，最终持久字段待接口适配），与通用 updatedAt 分开。

处理器已增加可选 contentEditedAt：给定时用于长文编辑时间兜底，来源标为 content-editedAt；显式 null 保持未知，不退回属性更新时间。未提供时保留上一版 updatedAt/原始 updateTime 的兼容输入。处理器算法版本升级为 2；它不负责给旧 Entry 批量添加字段。

已有手打时间仍优先。消息 sentAt、评论 createdAt、图片 insertedAt 与正文时间互不替换。保存适配前必须明确历史旧篇的时钟来源；2915 篇原始时间已保留、3 篇存在原始/当前修改时间差异，不可隐式全取现在的 updatedAt。

## 4. 当前实际缺口，不能跳过

| 接点                      | 源码/合成核对结果                                                                                        | 放行要求                                                                               |
| ------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 旧 HTML/Markdown 属性保存 | 现有 validateEntry＋replaceEntry 可保留原正文/Markdown、附件、legacy、评论和未知原字段                   | 接新框架后继续跑同类往返和真实快捷窗用例                                               |
| 新 richdoc 正文写入       | 纯处理器已有；旧 validateEntry 仍只接 html/markdown                                                      | 新版能力判断、保存/恢复/旧客户端保护全部完成再启用                                     |
| 分类改名后的聊天配置      | taxonomy 路由改 Entry.category，但未同步 chatJournal.rooms/category 分篇边界；旧会话配置会被分类校验拒绝 | 统一改名/合并/删除的关联映射；聊天本地配置也需更新，不能只修服务器一份                 |
| 聊天归篇正文只读          | 当前 validateEntry 仍允许修改归篇 HTML，后续追加会把它识别成人工改动                                     | 服务端拒绝正文改写、保留属性管理；旧 UI 禁止误编辑但服务端不能只依赖按钮               |
| 聊天发送/接收             | 当前 shiye-journal.js 为本地聊天 → 日记归篇＋回执重试；尚无日记库 → 聊天通用消息订阅/接收层              | 新消息统一 envelope、来源/身份、接收去重、引用、附件、撤回和游标恢复；不能说已完整双向 |
| 旧日记进聊天阅读          | 原格式还在，尚无统一旧篇到聊天视图的来源适配                                                             | 分格式安全读取，原日记不改写，回看只投递来源引用，不重复导入成新消息                   |
| 属性修改的内容时间        | 现有 Entry 更新会统一改 updatedAt                                                                        | 新适配维护内容时钟；只改属性不移走回看时间，不把旧库批量改成当前时间                   |
| 性能与 UI                 | 纯处理器不依赖 DOM，但 async 在摘要计算前仍有同步工作                                                    | 不在每个按键/IME 组合中运行；接服务端/worker/受控保存任务，再实测输入延迟              |

上表后三类业务能力仍属于后续基础接口/回看阶段，不为本次要求偷偷改正式路由或重启另一会话的窗口。合成核对只是发现缺口，不把它当修复完成。

## 5. 接入放行顺序

1. 保持旧编辑器/宿主正常运行，先在隔离新篇中替换正文控件适配，沿用原保存与关闭握手；标题、分类、上下篇、工具入口不重排。
2. 验证新格式保存/重开/图片原件/恢复，以及旧格式继续编辑；新旧混合库同分类/标签筛选均能命中。旧图位置未知继续保留附件，不猜 Word 式排版。
3. 修复分类/标签关联和聊天只读边界，再接统一消息收发。新正文与 Record 属性分别取当前版本，任何冲突保留窗口和输入，不无条件覆盖。
4. 实测原快捷窗四核心、IME/空格、缩放/窗口记忆、自动保存/后台恢复和图片查看；处理算法不能改变这些交互。退化则保留原路径，不把未完成状态交给用户当新版。
5. 前两阶段基础数据稳定后，才开放朝花夕拾与只读原篇窗口；评论目标不因分类或时间规则改变而重算。
