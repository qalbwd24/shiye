# 文件管理、验证与交付

## 数据与源码分开

正式库只在 data；日常开发库在 var/dev-data；手动真实备份验收会新建 var/manual-imports/run-*。自动测试使用临时隔离目录，结束后只清理自己的目录。

上级研究材料、原APK、原Windows安装包、模拟器与真实大备份验收结果继续保留原用途，不混入应用源码。旧tests/ui-test-data保留作历史界面验收材料，不再是npm run dev的工作库。

`.gitignore`、`.prettierignore`与打包白名单分别控制版本管理、格式化和交付范围。这三件事不等价：尤其不要以为一个文件被Git忽略后，手动压缩整个项目就不会带上它。

## 常用检查

- `npm run check`：文件依赖和前后端边界、ESLint、Prettier、全部自动测试。
- `npm run check:files`：只读检查模块相对路径；不访问正式日记。
- `npm run dev`：18766端口的独立库，用于界面验证；可在启动终端Ctrl+C结束。
- `npm test`：自动发现.test.mjs；不执行tools/manual，不连接官方服务。

格式化工具只改源码和文档，排除data、var、vendor、资源原包、历史归档与旧界面数据。Windows PowerShell脚本使用UTF-8 BOM，避免中文路径被系统旧版PowerShell误读。

## 构建与源码交付

`npm run build:launcher` 调用系统.NET Framework编译器，读取 desktop/Launcher.cs，输出根目录exe；生成中间文件在build。端口取config/app.json。已运行的Node服务需要单独重启才能加载后端修改，仅重新编译exe不会更新运行中的服务。

`npm run package:source` 把明确列出的源码、配置、测试、文档和兼容资源复制到var/packages的新目录，每个文件记入SOURCE-MANIFEST.json，含相对路径、大小和SHA-256。包中没有正式库、个人备份、开发库、旧验收内容、node_modules或已编译exe；依赖可用npm ci恢复，exe可本机重建。

这是一个源码交付目录，不是安装器，也不是用户日记备份。迁移自己的日记应使用应用的加密备份功能。

## 更新与回退

这次结构整理前的源码保存在：`F:\我的奋斗\迁移记录\代码规范化前-20260914`。它不含正式媒体库。配套保存了正式diary.json的整理前哈希，用于核对本次操作是否碰过工作库。

后续更新顺序：先记录版本并保留源码快照 → 在独立库验证 → 正式应用保存完成 → 关闭旧服务 → 替换源码 → 重启并核对health版本 → 验证列表与相关操作。

如果代码更新失败，停止新进程后恢复之前的源码即可；不要顺手用旧工作库覆盖当前日记。只有涉及schema迁移时才使用专门的数据回退方案。当前版本并未更改schema。

关闭应用窗口不会自动停止Node服务。处理进程前应按监听端口和完整命令行确认属于此项目，不要终止其他Node进程。已有本地锁会话在重启后需要重新解锁。

## 历史归档

- docs/archive：拆分前代码等历史参考，不参与构建与检查。
- tools/manual/archive：旧真实库脚本的文本副本，已改为.txt，防止直接执行旧路径／旧端口写入。
- docs/validation：当前版本验证记录；旧验证记录明确注明所属版本，不把它当作最新验收。
- var/packages和var/manual-imports可能包含大型文件；需要清理时先检查完整路径和用途，不能对data执行通用清理命令。

本轮不会处理此前因自动审批保留下来的E盘迁移副本，也不会改变荣耀输入法修补或安卓虚拟机。

## 0.5 版本管理

开发分支 codex/desktop-v0.5 从 2925e6f 开始；旧第四版 main 保留。正式入口切换使用独立发布分支，不执行 reset --hard 或 git clean，不覆盖 data。升级前保存 diary.json 本地快照；需要回退代码时保留当前数据，不能用第三版数据副本覆盖新写日记。独立开发服务端口 18767 仅用于本轮隔离验证，日常 npm run dev 仍为 18766。

用户已明确要求每次更新启动新版，常规重启不再重复请求同一授权。交付必须核对健康接口版本；源码变更不等于服务更新。从旧第四版切换可使用已准备的 tools/upgrade-v05.ps1；日常同目录版本重启使用 tools/restart.ps1。工具层审批策略不能由项目脚本修改或绕过。
