## 2. 成熟方案比较

### CouchDB式变更流、版本与检查点

[官方复制协议](https://docs.couchdb.org/en/stable/replication/protocol.html)以变更流和检查点恢复复制进度；[冲突模型](https://docs.couchdb.org/en/stable/replication/conflicts.html)说明并发版本及应用层合并责任。借鉴点是按逻辑记录追变化，不依赖每次文件扫描；保存断点后只取新变化。默认胜出版本不代表业务已解决冲突。

完整改用CouchDB/PouchDB可列为原型候选，但会牵涉现有本地存储、原生桥、多实体事务和副本冲突处理。当前不直接更换数据库或宣称兼容其复制协议。

### WatermelonDB式本地脏记录、pull/push和字段跟踪

[实现说明](https://watermelondb.dev/docs/Implementation/SyncImpl)提供本地变化跟踪、同步中继续编辑以及字段级合并的参考；[后端协议](https://watermelondb.dev/docs/Sync/Backend)强调一致视图、删除记录和事务。适合参考客户端outbox、不同字段合并和确认时不误清新编辑。

其默认per-column client-wins不是拾页正文/撤回的既定规则，不能原样套到同段文字或历史消息。现有Android并非已接WatermelonDB，不因调研而引入新客户端框架。

### Replicache式持久mutation、确认与rebase

[官方工作原理](https://doc.replicache.dev/concepts/how-it-works)展示本地修改立即可见、后台提交、确认以及在新服务端状态之上重放未确认操作。适合借鉴“基准状态＋待发操作”的分离，解决收件覆盖本地输入、回执迟到误清队列。

这不是采用其SDK或照搬所有冲突规则的决定；服务端对批量操作的幂等、授权和事务仍必须实现。拾页需为媒体上传、撤回和绑定设置专用业务命令，不重放有外部副作用的动作。

### Yjs/Automerge CRDT

[Yjs updates/state vector](https://docs.yjs.dev/api/document-updates)支持交换缺失更新，更新可重复/乱序应用；[编辑器绑定](https://docs.yjs.dev/ecosystem/editor-bindings)提供成熟编辑器接缝。[Automerge冲突规则](https://automerge.org/docs/reference/documents/conflicts/)与[富文本](https://automerge.org/docs/reference/documents/rich-text/)说明结构化并发编辑能力及同属性冲突仍需处理。

若未来经常在两端同时逐字编辑同一长文，可对单篇长文原型验证CRDT。它需要额外的历史/身份/编辑器状态，不能把普通richdoc JSON数组直接当CRDT；图片出现身份、撤回清理、旧格式保护及跨端撤销仍须适配。当前多端协同不自动等同多人逐字共同编辑，不先把全部业务对象改成CRDT。

### ShareDB/OT

[ShareDB官方介绍](https://share.github.io/sharedb/)提供基于OT的JSON实时协作和重连机制。适合专门的共享文档协作；操作变换类型、服务器顺序和富文本适配均有成本。保留为同篇协作候选，不以它替代分类、媒体、设置和整个库的同步协议。

### rsync与Syncthing文件/块增量

[rsync原始算法](https://rsync.samba.org/tech_report/node2.html)面向相近文件的块差分；[Syncthing BEP](https://docs.syncthing.net/specs/bep-v1.html)提供索引序号和块交换参考。适合大媒体断点/缺块补传和导入校验，但字节差分不能决定两段正文谁覆盖谁、分类改名含义或撤回优先级。

不能把电脑、手机、服务器的diary.json/SQLite/IDB直接当三个普通文件互相覆盖。新照片/视频通常是新增不可变资源，按hash查缺并分块续传，比每轮计算全目录差分更直接。初期固定分块；内容定义分块/更复杂文件差分等以后用实际大文件收益验证。

### JSON Patch与三方合并

[RFC 6902](https://www.rfc-editor.org/rfc/rfc6902.html)定义补丁表达方式，不自带离线冲突算法。对richdoc数组索引的补丁必须绑定基准版本，否则前面插入一段后索引可能指错。三方比较可借鉴[Git合并](https://git-scm.com/docs/git-merge)的共同基准思路，但不对日记HTML/JSON运行字符串合并后就认定语义正确。

## 3. 初步推荐：分层组合

推荐原型方向是：**本地完整数据＋事务outbox/inbox＋服务端按库有序变更日志/断点＋版本校验/三方字段合并＋资源hash/缺块续传**。这是对成熟机制的组合设计，不是已实现的新算法，也不宣称与上面某个产品协议兼容。

| 层       | 推荐机制                                         | 避免的问题                             |
| -------- | ------------------------------------------------ | -------------------------------------- |
| 发现变化 | 所有业务写入同时登记change，不靠正常同步扫描全库 | 漏掉分类/壁纸/后台写入，反复逐文件比对 |
| 可靠提交 | 持久operationId、不可变请求、事务回执            | 回执丢失重复创建、操作ID复用改了正文   |
| 增量接收 | 按库有序seq、稳定快照、水位/游标                 | 翻页期间新写入漏收、只看时间戳导致跳过 |
| 本地体验 | 基准副本＋待同步覆盖层，确认精确到操作           | 收件覆盖草稿，旧ACK清掉新输入          |
| 冲突     | 对象/字段级三方比较；危险情况保留双方            | 整对象LWW丢字段，同段正文静默覆盖      |
| 文件     | 原件不可变、授权内hash复用、分块清单             | 每轮重传/重hash全库、GIF被缩略图替代   |
| 实时     | 提交后通知有新序号，重连按游标补齐               | 将WebSocket在线消息误当可靠存储        |

正常一次同步的工作应与变化记录数和缺失媒体字节相关，不与全部历史文件数线性绑定。首次装机、已确认的索引损坏修复、服务器恢复/日志过期是需要快照或重新对账的明确例外；不能承诺任何情况下都零全量。实际复杂度、吞吐和耗电尚未测。

## 4. 正文与零散资料采用同一同步框架

必须登记的逻辑对象包括日记/消息、会话及其设置、分类/标签和顺序、资料/头像/裁切、壁纸引用/外观、媒体/收藏/命令映射、服务实例配置及绑定、评论/投递。各类对象有独立ID/版本，但共享一个账户日记库的变化流，避免每类独立游标错过跨对象事务。

电脑改壁纸、手机改会话名：两个字段可合并；双方离线都改壁纸：保留两个资源和冲突记录，不能把另一端图片当垃圾清掉。分类按稳定ID改名，不把改名误判成删旧类建新类。两端会话编号/分类现存格式不同，需要兼容映射；此处是适配建议，不谎称已存在所有逻辑UUID。

哪些外观属于共享默认、哪些允许本设备覆盖，需要列白名单：会话壁纸、头像与分类同步是用户已确认需求；窗口坐标/显示屏/DPI等建议仅本机；字号/主题是否强制同值、草稿是否跨端为待选项。即使提供本机外观覆盖，原始壁纸/头像及共享默认仍按已确认范围同步。

## 5. 朝花夕拾部署方向

用户现已确认目标由服务器根据客户端提交的参数执行，不再把“以后放哪里”列为完全未定。客户端编辑服务实例配置/绑定，服务器持续调度并持久化抽选、游标、投递和评论；变化经统一增量协议到各端，本地完整保留已收到的数据。

每个服务实例是一个逻辑执行者，不让每台设备按相同配置都抽一遍或推一遍。客户端不可上传旧cursor/randomDays/投递历史覆盖服务器进度。配置修改基于版本；普通保存不兼作补发。设备变化流游标、服务调度游标、旧实例feed序号是三种不同含义，不混用。

现有conversation-services已提供实例/绑定和本地host基础，可保留业务逻辑，云端另接认证/持久调度宿主。本机仍沿现有链路测试/使用；本轮不迁移旧revisit单例、不重置日期或游标，也不改既有评论固定关联。

## 6. 后续最小验证与决策门槛

1. 补统一同步对象清单和变更捕获端口，先明确哪些写口/本地偏好还没接，避免“正文能同步就算完成”。
2. 用隔离合成库＋两个持久模拟客户端验证对象增量、回执丢失、同步中继续编辑与断线恢复。无变化只读游标/心跳；改一条只枚举相关对象和媒体，不扫描全部资源。
3. 扩到会话名/壁纸/头像/分类/收藏，双方离线改不同字段可合并、改同字段可见冲突，删除/撤回不能复活。
4. 接真实客户端Repository和保留式迁移，核对完整Entry/未知字段、legacy映射、媒体字节、光标/IME和手机离线完整资料；再做局域网/云端。
5. 若同一长文并发编辑频繁且冲突体验不可接受，再比较块级三方合并与单篇CRDT/OT原型。不得用“自动合并了”代替富文本结构/时间/媒体出现/评论锚点验证。
6. 服务实例云执行与参数配置单独联调，验证两端配置冲突、服务器重启、旧进度保持和单次投递，不因同步重启本机正式任务。

本次按TESTING-POLICY只检查新增文档格式、引用和源码盘点脚本，没有改业务代码，未跑产品全量/原生/浏览器矩阵。后续算法必须经过上述验证才能称“可靠互通”；本报告未提供虚构的性能或成功率。
