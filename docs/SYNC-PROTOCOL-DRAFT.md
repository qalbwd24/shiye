# 多端增量协议与冲突规则草案

2026-10-18 本文保留研究依据；本轮已经实施的协议/API以[SYNC-BACKEND-IMPLEMENTATION](SYNC-BACKEND-IMPLEMENTATION.md)为准。用户最新同字段规则为较晚服务器提交作当前主版、另一份进同实体冲突历史，不另建普通记录；撤回墓碑优先。独立服务尚未接管正式业务库或客户端。

2026-10-18。状态：研究后的候选协议，尚未实现端点、迁移或修改当前schema。用户确认的范围与算法来源见[调研报告](SYNC-ALGORITHM-RESEARCH-2026-10-18.md)；本文把工程约束写到可供原型验证的程度，不把字段建议冒充现存API。业务格式继续以[电脑/Android实际内容契约](DESKTOP-ANDROID-CONTENT-CONTRACT.md)为准。

## 1. 同步对象与字段所有权

建议同一账户日记库使用统一变更流，各对象有独立逻辑ID和serverRevision。类型名仅为草案，下面不要求现有JSON物理改成这些表。

| 逻辑对象                    | 需要同步的数据                                                            | 编辑权/当前适配                                            |
| --------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------- |
| journalAggregate            | 完整Entry信封、richdoc/原格式、元数据；canonical时的unit/layout与身份映射 | 两端从长文入口提交；规范化相关变化同事务，不能各自双写     |
| chatMessage                 | 规范消息、原sourceId/roomId/messageId映射、正文/时间/引用/媒体/撤回       | 两端可新增/撤回/按原语义重发；收到消息不能换成本设备新身份 |
| conversation                | 稳定会话ID、名称/描述、分类关系、壁纸/头像引用、归档/置顶与顺序           | 两端可改；旧TL数字ID和desktop命名空间通过映射保留          |
| taxonomy / relation / order | 分类/标签身份与名称、归属关系、排列                                       | 两端可改；电脑名称引用与Android categoryId不能直接混用     |
| appearance                  | 会话/共享默认主题、背景/气泡等可移植参数，资源引用与裁切                  | 用户已要求壁纸/头像同步；每字段白名单，设备覆盖另存        |
| profile                     | 名称、签名等长期资料，头像原件引用及裁切                                  | 两端可改；修改当前资料不回写旧消息的历史身份               |
| asset                       | 媒体ID、hash/大小/MIME、用途、原件可用性及上传回执                        | 客户端创建/传原件，服务器验证；路径/Blob URL不入协议       |
| sticker / commandMapping    | 收藏名/分组/资源、emoji/表情命令映射与删除标记                            | 两端可改，收藏删除不删除原消息或共享资源                   |
| serviceConfig / binding     | 实例参数、启用、provider/instance/conversation绑定、发送者配置            | 客户端版本化修改，服务器校验；多个实例相互隔离             |
| serviceOutput / comment     | 投递引用、抽选结果必要展示信息、评论/固定目标及撤回                       | 服务器产出投递；客户端只提交评论业务命令，不伪造投递状态   |

设备本机状态建议单独命名空间：窗口尺寸/屏幕/DPI、本机路径、网络状态、正在选择的文件、认证密钥与临时预览URL不跨端覆盖。字号/输入偏好/主题/阅读位置/草稿是否跨端仍需细化；草稿若同步，应按设备或草稿ID保留多个，不以同一字符串互相覆盖。

本地永久资料与可重建缓存分开。手机/电脑按已确认目标都长期保存完整资料/原件；缩略图、DOM、TL投影、搜索索引等可以重建，但现有原型IDB在切换权威前不能直接删除。

## 2. 正常同步不全量扫描的前提

每个受支持写入口必须把业务提交与变化登记写在同一事务：长文、聊天、分类改名/合并、会话管理、外观、收藏、导入、后台朝花夕拾/评论、删除恢复都不能漏。前端localStorage/资源IDB的便捷写入口需逐步改为Repository命令或显式适配，不能事后靠比较所有文件猜变化。

当前全库JSON存储没有此变化端口。过渡若把日志放同一JSON中，可保持原子提交但仍有全库序列化成本；若日志另放SQLite而源数据独立JSON写入，两者不是天然原子。云端建议让业务行、去重回执、变更日志处于同一事务存储；现有mutate保留为本机兼容端口，迁移方案另验。

正常查询以有索引的库/账户范围seq、未确认outbox和媒体任务状态为入口，禁止为每次sync计算所有对象/文件hash。初次引入现有资料或首次导入可做一次受控盘点；后续新资源只hash一次，外部篡改/损坏校验是显式修复流程。

## 3. 版本、序号与候选信封

- entityId是业务身份；serverRevision是对象在云端的版本；localRevision表示本机编辑代次，两者分开。
- operationId表示一次不可变业务操作；同ID重试须保持请求摘要/目标/内容完全一致，改变请求应创建新操作，旧ID不同摘要应冲突。
- deviceId和本地计数用于来源/顺序/诊断，不替代全库内容身份，不靠客户端墙上时钟仲裁。
- changeSeq表示同一库已提交变化的顺序；eventTime、insertedAt、updatedAt、朝花夕拾调度cursor和实例feed sequence均不能替代它。
- cursor建议是绑定libraryId、serverEpoch、协议/schema与授权范围的opaque令牌。恢复服务器/换库后不能拿旧seq当同一历史继续。

虚构的会话改名操作示例（不是已有端点请求）：

```json
{
  "operationId": "op-demo-001",
  "deviceId": "device-phone-demo",
  "entityType": "conversation",
  "entityId": "conversation-demo-001",
  "baseRevision": 7,
  "command": "updateFields",
  "changes": { "title": "灵感" }
}
```

changes只表达用户实际更改的白名单字段。未发送字段与显式null/清空不同；不能把整个旧设置对象PUT回去清掉另一端新壁纸或未知新字段。原生写口的expectedRevision与云端baseRevision须由适配器明确映射，不混用本机递增版本。

服务端按操作返回逐项accepted/conflict/rejected及规范版本/身份映射。一个业务事务可有多对象变化，并携带transactionId/依赖；同一长文与其unit/layout、分类合并与引用重定向、实例绑定与关联校验须原子提交。无关会话的冲突不应无限阻塞整个账户同步；同一对象的依赖操作保持顺序。

## 4. 推送与本地未确认编辑

1. 本地事务保存业务状态、localRevision和outbox；媒体新文件先安全落盘，再提交引用和媒体任务。只有持久提交成功才ACK本地保存。
2. 发送选定outbox操作的不可变快照；记录发送时localRevision。已发但回执未知时不更改操作正文，不合并进新请求继续复用ID。
3. 服务端鉴权→查operationId回执/摘要→核对基准/依赖/字段权→业务事务更新＋去重结果＋变化日志→提交后回复。
4. 若服务端已提交但响应丢失，客户端用原operationId重试/查回执；不会重新生成消息/服务实例或重复撤回。去重承诺依赖记录保留/设备世代策略，不能随意清表后继续接受旧操作。
5. ACK只确认原操作。发送期间用户又从localRevision=10改到11，不能因10收到ACK就将11标成已同步。保存新远端基准，保留剩余本地操作，在新基准上重放安全业务命令或产生冲突。
6. 接收远端对象时区分基准存储与本地待改覆盖层，不能让inbox反过来生成同一条outbox造成回音。当前编辑器已有输入/IME/附件时不得直接替换正文或重置光标。

不承诺跨网络“消息永不重复到达”；采用允许重复传输、幂等应用和事务，保证同一操作只产生一次业务效果。对外副作用如以后AI/提醒投递需要各自幂等键，不因rebase重跑外部调用。

## 5. 拉取、快照与日志保留

### 正常增量

客户端提交已持久确认的cursor；服务器在一致视图中选择水位W，读取`cursor < seq <= W`的变化并分页。日志至少记录对象ID、对象版本、动作、transactionId和必要字段信息，避免将永久明文正文副本塞进审计日志。

实现必须保证seq与提交顺序相容。当前单写者方案可在同一串行事务中分配；将来并行数据库中，普通自增序号若先拿号后晚提交，可能被高水位越过，必须有提交有序机制，不能直接假设sequence等于commit顺序。

分页须带一致快照/固定变化包或版本化读取。仅取一个maxSeq、之后逐页读取随时变化的current行不够：行更新到W之后可能在页间消失，造成遗漏。第一页到末页的相关版本及跨对象事务边界需要有保证；超大事务可分片暂存，完整后一次本地可见。

客户端每页在一个本地事务中应用inbox、记录去重状态与新cursor。先推进cursor再写对象会漏数据，先写对象后崩溃则允许重复收到并幂等处理。未知实体类型/更高schema不能默默跳过却推进总游标，应保留原包并明确要求升级或使用受版本化范围的独立订阅。

### 首次或重建

首次快照绑定W和服务世代，完成快照后从W补取变化；快照过程中发生的修改不能掉进空档。首次全量盘点是例外，正常同步无需每次重建它。

日志/墓碑压缩需要结合设备确认位置与保留策略；长期离线设备、服务器恢复、cursor超出保留窗口时返回明确resnapshot-required。客户端保留本地未发操作和必要基准，在新快照之上重新协调，不能清空本地库/队列后假装修复成功。快照和日志保存期限待后续容量与隐私要求确定，不在此猜固定天数。

## 6. 冲突规则：按语义分层

### 三方字段比较

在可信共同基准B、本地修改L与远端当前R之间：

```text
L == B → 接受R
R == B → 接受L
L == R → 相同结果
其他   → 该字段冲突，保留L与R
```

只在基准版本/字段变化可信且可用时自动合并；缺基准时返回冲突，不猜。合并不改变用户原eventTime或媒体insertedAt，server receivedAt另记。保存必要的基准校验/字段版本时必须考虑撤回后的清除要求，不将私密正文长期嵌入回执/日志。

| 情形                           | 初步处理建议                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------- |
| 电脑改会话名、手机改壁纸       | 两字段都保留，自动合并                                                                             |
| 双方改同一壁纸/头像            | 冲突保留两资源及版本，展示/选择方式待UI讨论；不静默删除失败方                                      |
| 长文正文与分类/标题分别改变    | 内容与不同元字段分别协调，原文时间不受分类名更新影响                                               |
| 双方改同一长文正文             | 第一期按正文整体冲突保留；独立稳定块的三方合并另做原型，通过结构/锚点验证后才放行                  |
| 同篇不同block编辑              | 有可信blockId与共同结构基准时可研究自动合并；数组索引/相同时间戳不够，涉及移动/列表/跨块删除先冲突 |
| 两端新增聊天消息               | 各自稳定消息身份追加，同步不改为收到时刻；显示排序不以云ACK序号替代eventTime                       |
| 已撤回消息的迟到发送/编辑      | 墓碑优先，不能复活；重新编辑按既有新消息ID/新发送时刻提交                                          |
| 同一类别改名与另端给日记选类别 | 稳定类别关系保持，名称显示新值；若目标已删除/合并，明确重定向或冲突，不悄悄复建类别                |
| 收藏删除与历史图片             | 只删除收藏关系，不删历史资源/消息                                                                  |
| 双方调整分类/会话顺序          | 使用带基准的move/排序事务；不发送旧全数组覆盖新加入成员。同锚点并发的确定性规则需原型验证          |
| 日记删除与另一端离线编辑       | 保留可恢复冲突与原文，用户决定恢复/另存；区别于聊天撤回，不能一律删除优先丢长文                    |

标签等集合应提交针对具体关系的add/remove，而不是整数组替换；并发增删同一关系的语义须明确，不能用集合简单并集让已删除标签复活。第一期可用关系版本冲突，未来确有需要再引入OR-Set等专用CRDT。

### 分类和会话身份的实际缺口

电脑当前以分类名称引用并在改名事务中更新多个引用，Android已用categoryId。需要同步侧稳定逻辑ID与legacy别名映射，保留旧Entry原件和公开旧字段的兼容投影。不能仅凭同名强行合并不同类别；离线同名新建的消歧规则需明确。没有适配前，类别改名实际触及多记录，就应记录所有受影响对象，不能只发一条新名称却让旧端失联。

会话建立稳定conversationId，保留旧`sourceId+roomId`映射；跨端收到同一会话不再各自创建新身份。服务绑定使用该稳定ID，不用标题、壁纸文件名或裸TL数字当主键。所有映射在本地和服务器持久保存，换机/备份恢复仍有效。

## 7. 媒体、壁纸与头像

资源ID、字节hash和出现/用途关系分开：相同图片可以作壁纸、头像、正文或表情包，多次正文出现仍有各自occurrenceId/insertedAt。头像裁切是独立可同步参数，缩略图可重建，原图/GIF/视频保持。

上传走登记→缺块查询/上传→校验大小和整文件hash→finalize可用状态。块传输可重试，finalize幂等；修改文件产生新版本/资源，不原位修改旧hash对应字节。媒体登记、临时文件与数据库并非跨系统天然事务，必须明确崩溃恢复、暂存归属和清理规则；不得直接清理所有未知文件。

服务器只查询本次变化所引用资源的可用状态，客户端只处理持久缺失任务，不每轮列全目录。去重限定授权库/用户范围，hash命中不等于获得下载权限。元数据先到可显示待传状态，原件完成另发可用事件。

两端完整本地资料的目标保持：新设备先可显示元数据/缩略图，后台继续自动补齐原件，用户可见剩余任务；不能将“文字已同步”写成“全部文件已落盘”。下载任务与元数据cursor独立持久化，cursor推进后也不会忘记待下载原件。

更换壁纸/头像、移除收藏不立刻删除文件。GC必须核对正文、历史身份、会话、资料、收藏与未完成任务的引用；同步删除和服务端空间清理是分开的协议。

## 8. 朝花夕拾由服务器执行

用户已确认此部署目标。客户端提交实例配置和绑定，服务器验证expectedRevision并持久化，独立任务根据参数执行；前端只渲染回执/来源和提交评论。原服务实例providerId/instanceId/bindingId概念复用，云传输适配另做，不复制客户端计时器。

区分三类状态：

1. 可双端编辑：启用、历史范围、换日/间隔/时区、分类筛选、发送者配置、会话绑定。
2. 服务器独占：随机抽选结果、规则运行版本、调度cursor、投递去重/序列、租约/任务状态；客户端只能读取/请求明确业务动作。
3. 每设备本地：已接收变化位置、当前页面、展开/折叠、待发评论队列、媒体下载位置。设备A读到来信不代替B确认收到。

规则切换基于服务config版本，服务器在同一事务确定生效边界及新规则版本，旧投递/评论目标保持。旧设备后来上传配置不能顺便回写整个旧state，导致重新抽日/重复投递。任务重启沿服务器进度恢复，多个执行副本使用持久租约/原子领取与幂等提交；租约失效的旧执行者需fencing/提交版本检查，不能仅靠内存Map保证云端多实例只运行一次。

后台生成消息/评论同样登记changeSeq；原来为本机host设计的窗口Cookie不作为云端无人值守身份。普通细粒度运行心跳不强制推到所有设备，只同步需要展示的业务结果/状态，状态详情可按需查询。

本轮不将本机朝花夕拾停掉或立即启云，不改变当前日期/游标/实例，不重新解释既有引用/评论对象。算法云化与同步内核分开验收，可复用业务模块。

## 9. 隐私、删除与兼容性边界

撤回只能保证服务器后续不再提供原文、已连接客户端及时清除其活动缓存；离线设备在再次连接前无法被远程即时抹除。重新连上先应用撤回/权限失效，不从旧快照/本地备份复活。

变更流、快照、冲突副本和merge基准也受撤回/权限策略约束。日志优先存标识/版本而非明文；如为传输/合并暂存内容，需要过期/撤回清理和访问校验。公开接口不得通过历史revision或同步快照绕过当前撤回/权限。备份保留/恢复另遵从明确策略，不能承诺撤回即时物理消灭所有离线备份。

跨端传输能力版本、正文schema、派生算法版本、应用版本分别声明；保留未知字段，不因旧端渲染不了而回传裁剪后的对象。当前本机Host/Origin保护保留，远端使用独立认证授权入口。

## 10. 原型验收清单（待实施）

- 无业务变化不扫正文/媒体目录；一条消息、一次壁纸变更只查询相关变化和资源。
- 服务器提交后丢ACK、客户端应用后未写checkpoint、重复/乱序接收，均不丢/不重复。
- 发送中继续输入，旧ACK不清新版本；inbox不生成重复outbox；IME/光标/滚动保持。
