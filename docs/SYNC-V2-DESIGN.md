## 1. 基本分工

```text
电脑界面 ↔ 电脑本地数据/媒体 ↔ 持久待同步队列 ─┐
                                               ├─ 同步API ↔ 服务端事务存储/私有媒体
手机界面 ↔ 手机本地数据/媒体 ↔ 持久待同步队列 ─┘       │
                                                    变更通知
```

- 界面读取本地内容，输入、缩进、时间戳、图片预览等不等待网络；未下载媒体以明确占位表示。
- 本地保存与加入待同步队列应在同一持久事务内完成。界面可以即时显示输入，但只有落盘成功才标“本地已保存”；发起异步请求不等于保存成功。
- 同步工作器独立处理上传、重试和下载；收到服务端确认后才标“已同步”。应用退出/进程被结束后，本地队列仍应可恢复。
- 服务端只按已认证身份受理数据、校验版本/引用、事务落库、分配变更序号并提供增量读取。服务器有自己的持久存储，不能只当两个在线窗口之间的临时转发器。
- 长文仍以整篇Entry.body编辑保存，由已有规范化路径维护unit/layout的一致性；不让前端同时独立提交两套可分歧正文。该现有校验/规范化可保留在服务端适配层，不需要为同步把切分算法在两个客户端各重写一份。

统一格式表示内容身份和语义相同，不表示Windows/Android/云端必须采用同一数据库文件或每次上传完整diary.json。现有存储实现可以不同，必须通过适配层保真往返。

## 2. 保留的内容与新增同步信息

沿用现有Entry、MessageUnit、shiye-richdoc v1、会话归属、分类/标签、图片/视频资源及出现身份、手打时间解析和引用/评论关系。同步不重生成已有ID，不改写历史时间；旧篇使用已有读取/转换副本路径，不就地覆盖旧库。设置是否跨端按具体项目确认，窗口位置和设备尺寸默认留本设备。

同步层围绕现有写入命令增加以下传输信息，具体字段仍为候选：

| 信息                    | 作用                                                                   |
| ----------------------- | ---------------------------------------------------------------------- |
| 稳定记录ID、设备ID      | 两端知道是哪条内容、哪台设备产生；收到另一端内容不再当成本机新消息上传 |
| operationId             | 同一次操作断网重试仍算一次，不重复创建或撤回                           |
| baseRevision            | 表示基于哪个版本修改；版本不符保留冲突，防止旧设备覆盖新内容           |
| 服务端变更序号/设备游标 | 按上次确认位置补齐变动，不靠设备时钟猜谁更新得晚                       |
| 内容格式版本            | 旧客户端遇到不支持的内容只读保护，不能转纯文本后覆盖                   |
| 撤回/删除墓碑           | 传播状态，离线旧副本不能把原文恢复                                     |
| 媒体可用状态            | 区分本地原件、上传中、服务端可下载、失败，不把断网当文件已丢失         |

不将updatedAt当同步游标；eventTime/insertedAt与服务端接收时间分开。长文新增/拆合后的规范消息ID映射仍由现有内容写口处理，网络层只转发并保存回执，不拿本地气泡整数编号替代规范ID。

## 3. 怎样做到流畅

1. **显示先读本地。** 打开会话/日记先呈现已有内容，网络更新随后应用；翻页只取所需记录，不加载全库全文和全部原图。
2. **输入保存与上传分开。** 本地保存及时完成，短时间连续编辑可以合并待上传版本，避免每个按键都触发全篇上传。合并只针对尚未发出的可替代同篇版本；已发但回执未知的操作必须用原operationId核对，不能随意换正文重试。
3. **后台处理重活。** 媒体哈希、缩略图生成、压缩以及大数据序列化避免阻塞界面线程，限制并发；保持原图/视频字节，压缩使用既有明确选项，不因同步默认重复压缩。
4. **文字不排在大视频后面。** 文本变更与媒体分队列，有带宽/并发限制。对端先收到文字和媒体占位，上传完成再更新可下载状态；UI区分正文已同步和附件仍待上传。
5. **远端更新不能打断写作。** 当前编辑篇已有未提交改动时，不用远端内容覆盖输入框、重置光标/IME或滚动位置。无冲突才更新本地；有冲突保存双方版本并提示。列表/非编辑消息局部更新，避免每次收件全量重建。
6. **失败可恢复。** 退避重试、重开续队列；失败状态可见，不阻止继续本地写入。队列长度、上传进度和错误仅记录必要状态，不把私人正文写调试日志。

具体防抖毫秒、批量大小与媒体并发数通过隔离测量后决定，不把猜测参数写成已验性能保证。流畅性同时验输入响应、首屏显示、滚动稳定、内存/电量与真实网络恢复。

## 4. 实时传输与可靠同步

建议先实现可靠的HTTPS请求协议：提交变更、按游标取增量、首次分页快照、媒体上传/下载与完整性确认。下面是逻辑能力清单，不是已经新增的公开API：

- 提交操作：返回已提交的operationId、规范ID/映射、版本和服务端序号。
- 读取变更：从设备已确认游标继续分页，明确是否还有下一页。
- 首次同步：快照必须绑定确定的起点/版本，快照期间新产生的变更可在随后补取，不能出现快照与增量之间的空档。
- 实时通知：服务端提交后通知在线设备“有新序号”，设备再取增量；连接断了按原游标补齐。
- 媒体：上传会话/分块或可重试整文件、原件hash/大小确认、下载授权和可用性查询。

实时通知建议使用WebSocket（或同类服务端事件通道），但它不代替持久队列/变更日志。通知丢失、重复或重连不会影响最终完整性。第一次最小联调可先用手动同步或短轮询证明数据正确，随后加实时通知满足在线自动同步；不能将临时轮询演示当成最终实时指标。

“实时”针对在线且应用能联网的设备。离线时本地照常用，联网后补齐；Android后台/强制停止时能否即时联网另受系统限制，当前不承诺杀进程后实时到账或接入系统通知。原本本机服务保留回环限制，新同步服务使用独立受保护入口，不通过取消现有安全检查把所有本地路由开放到局域网/公网。

## 5. 从零开始的实际顺序

### 第一步：独立同步内核，加两个模拟客户端

先在电脑开发一个使用合成库的新同步测试服务。两个后台客户端分别充当电脑和手机，各有独立本地库/设备ID/队列。先只支持一条普通消息和一个长文条目的创建/读取，沿用真实格式，完成A写→服务器确认→B读取，以及B写→A读取。

再测：重复提交只有一条；收到远端内容不二次创建；关掉一个客户端后重开能补取；服务端保存后回执丢失仍可核对。该步无需买云服务器，不操作正在使用的客户端或私人日记。验证脚本、临时库和产物在明确授权实施时按outputs/与tmp/单独建目录。

### 第二步：两端分别接同一个数据适配接口

电脑与Android客户端各实现本地Repository/同步适配层，前端继续使用原来的编辑和显示组件。保留电脑原生桥、手机平台桥的职责边界，不照抄chrome.webview调用到Android。

只在隔离电脑实例和电脑上的Android模拟器中读写同一条测试内容，逐步覆盖会话/分类/标签。真实手机接入由用户选择时机；不因本设计默认操作或覆盖当前手机版本。

### 第三步：同一Wi-Fi上的真实手机与电脑互通

启动独立、明确允许局域网且带认证的测试服务，两端填写它的地址并配对/登录。手机访问的是电脑的局域网地址，不能填127.0.0.1（那指手机自己）。这里尚须开发正确的远程入口与客户端配置，当前本机API并不已经具备此能力。

用户在手机写一条，电脑看见；电脑写一条，手机看见。再拔网/重开/切Wi-Fi，检查本地写入和恢复。先文字、再图片、再视频；测试库与正式库始终分离。局域网认证/传输仅用于受控开发，正式远程必须有HTTPS。

### 第四步：补全离线、冲突、媒体和实时

两端离线写后恢复、同篇并改、分类改名、删除/撤回、媒体断点与hash、长文格式和引用/评论目标一致性都通过后，再加入即时变更通知。对正在编辑的页、输入法、字号/光标/滚动与大图/视频分别验收。

### 第五步：同一同步服务部署到自建服务器

业务协议不因部署变化再设计一遍，改为云端HTTPS地址，并完成账号/设备授权、私有存储卷、健康检查、备份恢复和版本回滚。换服务器地址涉及服务身份/数据归属验证，不能直接把测试库数据与正式待发队列混在一起。

先用合成库做公网两端联调，之后在旧库副本上导入真实数据并逐项校验，最后才切正式使用。旧日记原件、此前转换候选与新同步库保持可区分。朝花夕拾云调度、AI和提醒不在此步顺便启用。

## 6. 第一个可交付里程碑

**独立测试后台 + 两个持久模拟客户端，完成双向文字同步、重复重试防重、断线重开补齐。**

这一项打通后，客户端知道要调用什么接口，服务器知道保存什么，才进入真实手机/电脑联调。界面完成不等于同步完成；只写协议文档也不等于已经互通。

本轮成果仅本文和共享需求/交接更新，未实现上述服务。授权实施前无需先决定云端AI、提醒、云调度；是否采用服务器不可解密的端到端加密可独立讨论，本轮不以此阻塞合成数据同步内核设计，也不默认降低隐私要求。
