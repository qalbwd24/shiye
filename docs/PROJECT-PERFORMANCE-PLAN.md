## 目标与口径

降低常驻 CPU、私有内存和无用 I/O，改善打开、唤回、输入、发送、切换与保存。保留数据原件、历史格式、草稿、IME、位置记忆、媒体质量、保存保护和失败恢复。按入口/场景报告中位数、尾部时延和回收趋势，不用短测宣称长期泄漏已解决。

现有串行提交和 revision 冲突保护是数据一致性边界。先消除重复工作，不先换框架、迁移数据库或合并私人 profile。性能授权不等于把其他会话尚未验收的功能一起部署。

## 当前执行顺序

1. 随想ui16素材读取改进已验收上线，继续定位前台CPU。原生桥源码来源不同，不混合重编部署。
2. 便签重复保存图片已优化并完成浏览器验证；原生关闭/重开受启动策略限制待补。选区/目录遍历和多标签资源保留继续测量，避免改变撤销历史。
3. 主页/思绪共享编辑器重复转换已优化并验收；后端全库读写、无变化刷新进入下一批测量，再评估需要新契约的结构改造。
4. 分别验收四入口可见/隐藏/唤回、大文档/媒体与重复开关的资源趋势，再形成共用宿主策略。

这是主代理建议的执行顺序，随实测调整。每批记录问题、证据、改动、前后结果及未验范围，及时同步功能索引、需求、开发交接和验收记录。

- 同一ui15进程：非前台折叠约0.161%CPU，唤回后前台混合展开/折叠约3.897%，切到资源管理器后非前台折叠约0.171%，未重启。前台/几何/UIA/输入法因素尚未完全分离。
- 热点含宿主UI线程与browser CrBrowserMain。WPR无法启用系统剖析策略（0xc5585011），未录制、未提权。合成profile原生消息仪表已完成：完整ui15与简单textarea的进程树CPU均约2.52%，纯WinForms前台约0.47%；三者均约200次/秒WM_GETOBJECT。根窗口处理仅约9–10ms/秒，不能解释WebView宿主全部占用；调用来源、子控件和COM成本仍待定位，不关闭可访问性。
- ui16只改变5文件，21项真实IDB、15项浏览器、441＋10原生与591全项目检查通过，已标准升级及核验12215安装哈希。减少无关Blob返回不等于已证明RAM节省。
- 便签已实现只提交尚未成功落盘的素材对象，事务完成后更新跟踪，失败/替换保持重试；实际Chrome输入事务33.53→1.27ms（43.3MB合成素材）。原生启动被自动审批拒绝，不绕过，原生保存关闭/重开仍待补。

## 一手调研与适用边界

- [WebView2性能建议](https://github.com/MicrosoftDocs/edge-developer/blob/main/microsoft-edge/webview2/concepts/performance.md)：合理复用environment、释放不用的控件、评估后台内存目标与挂起。拾页有独立profile和后台保存/媒体，不能无条件合并或挂起。
- [WebView2线程模型](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/threading-model)：UI消息泵参与回调，宿主与网页开销须分开测。
- [Node.js事件循环开销](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)：大型JSON可能阻塞事件循环；先测阶段时间，不提前回保存成功。
- [Chrome内存诊断](https://developer.chrome.com/docs/devtools/memory-problems)：结合分配时间线和引用链；堆快照只用合成库，正式正文不进入报告。
- [Tiptap集成性能](https://tiptap.dev/docs/guides/performance)：检查周边重复更新。此页主要讨论React，拾页原生模块不照搬hook方案，应测现有事务/序列化/侧栏。
